## 4. 发版说明草稿骨架（`docs/releases/v1.0.0.md`）

沿用 [v0.2.0.md](../releases/v0.2.0.md) 的结构；`<>` 处按定稿事实填写，不预填成绩。

```markdown
# DexAtlas v1.0.0 — <主题句，如 "The Evidence-First Portfolio Release">

**One paragraph:** what v1.0.0 is, who it is for, and the one-sentence boundary
(static, evidence-first analysis; agent is bounded and its answers are leads).

## What's in this release
- **M5 — claims baseline.** Every outward claim re-checked against code and
  committed traces; three benchmarks regenerate byte-for-byte.
  [phase3-baseline.md](../reports/phase3-baseline.md)
- **M6 — frozen service regression set (20 questions).** Level-0 deterministic
  scoring 20/20; level-1 scripted drill proves the pipeline. Level-2 real-model
  batch: first three-round run scored 40% (45/40/35) — below the bar; after the
  root-cause fixes, the full three-round retest scored **49/60 = 81.7%
  (15/16/18 per round)** — still below the three-round ≥90% bar; the numbers
  and their limits are in [m6-level2-retest4.md](../benchmarks/m6-level2-retest4.md).
- **M7 — client-ready deliverables.** Offline single-file HTML reports
  (`analyze --html`), minimal evidence packages (`dexatlas export`), rewritten
  case studies. <逐例附件是否随 Release 附上，写实际做法>
- **M8 — installs, contracts, failure recovery.** `--workspace` on every
  command; the public contract table with 49 verified checks and snapshot
  tests; clean-install/Docker/recovery rehearsal; `EXIT_TRUNCATED` (5).
- **M9 — showcase.** Bilingual README refresh; Upwork materials remain
  unpublished drafts.

## What this release does NOT include
- No claim that the agent meets the service acceptance bar (post-fix three-round
  retest 49/60 = 81.7% vs the ≥90% bar; see
  [m6-level2-retest4.md](../benchmarks/m6-level2-retest4.md)); agent answers
  remain **leads**, never verified findings.
- No native/dynamic analysis — `DEXATLAS_GHIDRA_PATH`/`DEXATLAS_RIZIN_PATH` are
  reserved and unread.
- No plugin ecosystem beyond the tool registry.
- No published Upwork service page; no macOS verification (Windows/Linux tested).
- Not a security audit, penetration test, malware verdict, or packer/obfuscation bypass.

## Known limitations
- A run whose every code backend fails can still record `completed` when a
  manifest was parsed; it now answers **exit code 6 (`EXIT_NO_INDEX`)** instead
  of 0, and the same fact is detectable via `errors[]`, `index_complete == false`,
  or `completeness=partial` (contract table §8.1).
- Level-2 boundary: one model, temperature 0, first-party small APKs, closed
  20-question set; A/B vs DexAtlas ran under different budgets, so configuration
  differences are not model-quality claims.

## Upgrading from v0.2.0
- `analyze` now returns **exit code 5** when a step was truncated (was 0);
  0/1/2/3/4 meanings unchanged.
- Every command accepts `--workspace`/`-w` (additive).
- Agent default budget raised to 120,000 tokens / 16 iterations / 120 s, plan
  cap 40 steps (was 20,000 / 8 / 120 s / 12). Env overrides unchanged.
- Agent JSON report adds a `convergence` object; Markdown adds a "How the task
  converged" section (both additive).
- New: `--html`, `export`. Schemas unchanged: report `schema_version=3`,
  evidence package `1`.
- Install: `uv sync --extra dev --extra analysis --extra mcp --extra demo`.
```

## 7. 追加检查项 —— 这一轮实际踩到的坑

**补记日期：** 2026-11-17 · **补记基线：** `8524503`（分支
`claude/release-checklist-lessons-7b9767`）。

§1–§6 是发版的**流程**；下面八条是 v1.0.0 这一轮真实踩到、并且**已经改进过代码**
的地方——规则本身已经写进脚本、判据与文档，这里记的是「怎么确认它还成立」。每条
给出**怎么查**与**出问题怎么办**。§1–§6 不因此重排。

### N1 测量必须独占

- [ ] **检查项**：同一个 checkout 里不能并发跑测量。
  `scripts/refresh-report-figures.py` 给每次测量用**私有**的覆盖率数据文件
  （`measurement_data_file()` → `.scratch/coverage/<pid>/.coverage`，目录常量
  `MEASUREMENT_DATA_DIR`），并用环境变量 `COVERAGE_FILE` 通知它启动的每一个进程
  （`measurement_env()`；配合 `COVERAGE_RC` 的 `COVERAGE_PROCESS_START` 与
  `parallel = true` 才覆盖得到 worker 子进程）。同一 checkout 的并发测量由
  `.scratch/measure.lock` 的**操作系统级文件锁**挡住（`try_measurement_slot()`）：
  已有测量在跑时新测量直接拒绝并打印说明，不与对方抢报告——锁只在「写这份 checkout
  的报告」时取，随进程结束由操作系统释放。
  **怎么查**：`git worktree list` 看本机还有哪些工作树在跑东西；测量前后确认
  `.scratch/coverage/` 下只有本次运行的目录；再**问一句**同机器上有没有别的会话正
  在跑测量（锁挡得住同一 checkout，挡不住另一个会话同时改同一份文档）。
  **出问题怎么办**：等当前测量结束再跑，不要删锁文件；测量在跑时不要改任何会被它
  写进报告的文档——数字会在测量过程中漂。

### N2 不要用不带 `--cov-append` 的 `pytest --cov`

- [ ] **检查项**：改文档、跑子集测试时，`pytest --cov` 必须带 `--cov-append`。
  不带的话它把 checkout 根目录的 `.coverage` **整体替换**，并发时把正在跑的测量顶成
  残缺值——套件计数仍然正确、覆盖率却被换成一小撮覆盖面，报告与 README 徽章因此
  写出不实的数字（这一轮就发生过，规则已记进 CHANGELOG）。测量脚本自己的两个自检
  阶段用的正是 `pytest --cov=dexatlas --cov-append`（`measure_report_checks()` /
  `measure_status_checks()`）。
  **怎么查**：跑子集前先看命令行里有没有 `--cov-append`；没有干脆别跑 `--cov`
  （`uv run --no-sync pytest tests/test_docs.py`）；`.coverage` 已被 gitignore，
  要看它得用 `ls .coverage*`，不能靠 `git status`。
  **出问题怎么办**：`.coverage` 已被顶掉就必须**重跑完整测量**，不能只补跑一个子集
  ——报告的数字必须整份来自同一棵树。

### N3 报告数字落盘后才定稿

- [ ] **检查项**：测试数、覆盖率、徽章都由 `scripts/refresh-report-figures.py`
  生成，**顺序不可变**：改代码 → `ruff format` → 完整测量 → 再改引用这些数字的
  文档。格式化会移动行，报告记录的是源码树指纹，指纹在格式化之后就已经变了，所以
  格式化必须在测量之前；测量不完整（有 skip）时脚本拒绝写入并保留旧值。
  **怎么查**：核对 `docs/reports/phase1-execution-report.md` 里的 `<!--fig:...-->`
  是否已被脚本替换成数字；再跑 `uv run --no-sync pytest tests/test_docs.py`
  （`test_execution_report_coverage_figures_describe_the_current_code` 会核对记录里的
  指纹与当前树一致）。
  **出问题怎么办**：数字与文档不一致时改代码、**重跑测量**，不手改数字
  （CLAUDE.md 规则 3）；指纹对不上说明测量跑的不是现在这棵树，重跑而不是改数。

### N4 引用旧输出要用「」，反引号会被当成当前声明

- [ ] **检查项**：文档里**引用**别的文档或工具的旧输出（审计报告里的检查器输出、
  旧版自查结论、旧版本号）时，整段用项目的引述约定包起来：`「」`（也接受 `『』`、
  `“”`、`‘’`）。**反引号不构成引述**——它表示字面文本，会被
  `scripts/check-version-claims.py` 读成对**当前**状态的声明。
  **怎么查**：`uv run --no-sync python scripts/check-version-claims.py --base auto`，
  看是否有新增 finding；引用旧输出却没加引述的段落会在这里冒出来。
  **出问题怎么办**：把旧输出改成「」引述，或加「（历史记录）」之类的限定语；门禁
  指出的是一条真声明时改声明本身，不要改门禁去迁就它。

### N5 改动落地后统一重锚 `file:line`

- [ ] **检查项**：改过 `src/` 或任何被引用的文件之后，文档里的 `file:line` 锚点会漂。
  `scripts/check-doc-citations.py` 是权威；`scripts/remap-citations.py` 只在检查器说
  「符号已经离开被引用的行区间」时移动引用，且**幂等**（跑两次，第二次不改）。
  **跨文档引用要在所有改动落地后统一重锚一次**，不要边改边锚。
  **怎么查**：改动全部落地后依次跑

  ```bash
  uv run --no-sync python scripts/remap-citations.py
  uv run --no-sync python scripts/check-doc-citations.py
  ```

  并读检查器的输出（drifted 与 unresolved 都必须是 0）。remapper 默认处理检查器读
  的那四份文档（`docs/analysis-provenance.md`、`docs/architecture/public-contracts.md`、
  `docs/reports/phase1-execution-report.md`、`docs/benchmarks/large-apk.md`）；单份
  文档用 `uv run --no-sync python scripts/remap-citations.py docs/x.md`。
  **出问题怎么办**：remapper 修不了的是「指向地方而不是符号」的引用（它不猜），由
  人判断改成指向符号或改用文件级引用，再跑一次检查器确认。**注意机器够不着的地方**：
  Release 正文附录指向发版说明行号的引用（如 `docs/releases/v1.0.0.md`）不在检查器
  的四份文档里，漂了不会被报出来——那类引用只能人工重锚。

### N6 三份对外文本要同源对齐

- [ ] **检查项**：同一批对外数字出现在三处：`CHANGELOG.md` 的版本段、仓库内发版说明
  `docs/releases/v1.0.0.md`、GitHub Release 正文
  `docs/reports/v1.0.0-github-release-body.md`。三者必须**同源**；本轮的一致性复核
  （`docs/reports/release-notes-consistency.md`）列出了九处「一边有、一边无」的口径
  差异，其中两处会让读者直接误判（独立验收的边界只在一侧、验证数字只在另一侧）。
  **怎么查**：逐条对照三份文本的同一批数字（套件计数、覆盖率、层级 2 逐轮分数、
  源码指纹），把复核报告列出的差异列表逐项过一遍；每个数字都能在落盘报告里找到
  出处（`docs/benchmarks/m6-level2-retest4.md`、
  `docs/reports/phase1-execution-report.md`）。
  **出问题怎么办**：**以落盘报告为准**修正两份文本，发版说明与 Release 正文谁跟
  报告对不上就改谁；CHANGELOG 的版本段随之同步。三份对齐之后再发 Release，别先发
  再补。

### N7 自查脚本的判据不能写死版本名

- [ ] **检查项**：给自查脚本加判据时，判据跟着「**最新一节**」和语义走，不写死版本
  名或 `[Unreleased]` 字样。这一轮 `scripts/m10_selfcheck.py` 的判据写死了「CHANGELOG
  顶部要有 `[Unreleased]` 一节」；v1.0.0 发布后那一节被清空（Keep a Changelog 的正常
  形态），一棵**正确**的树被判红——那是判据过时，不是 CHANGELOG 的缺陷。判据已改为
  检查最新一节（发版前是 `[Unreleased]`，发版后是刚打 tag 的那一节），条目 id 相应
  改为 `DOC.changelog-newest-section`，判据表在 `docs/reports/m10-selfcheck.md`。
  **怎么查**：新增或修改判据时，在 `scripts/m10_selfcheck.py` 里搜判据文本，确认
  没有写死的版本号或 `[Unreleased]`；判据改了，自查报告里的判据表也要同步。
  **出问题怎么办**：先把「判据过时」和「文档真的错了」分开。正确的树被判红时改判据
  （并同步自查报告），不要改正确的文档去迎合判据。

### N8 对外材料的人设口吻会被读成真客户

- [ ] **检查项**：素材里的第一人称客户叙述会被读者读成**真实客户案例**。这一轮把
  `docs/case-studies/` 里的 "customer" 换成了不会被误读的词（`potential user` /
  `reader` / `developer`），并在
  [case-studies/README.md](../case-studies/README.md) 里点明**样本数与分析数的
  差别**：三篇走查涉及三个一方 APK，证据包只覆盖两次分析（demo 与 api-integration
  的包来自同一次运行）。
  **怎么查**：`grep -rin "customer" docs/case-studies/ docs/outreach/` 应为空；对外
  素材里每处第一人称叙述都要能回答一句「读者会以为这是谁的案例」。
  **出问题怎么办**：要么换词（不写 "customer"），要么在素材里点明样本数与分析数的
  差别；对外页与仓库内文档的口径必须一致。

## 8. 自动化覆盖与盲区 —— CI 不跑的那些门禁

**补记日期：** 2026-11-17 · **来源：** [ci-gate-coverage.md](ci-gate-coverage.md)（只读
复核）· **复核基线：** `claude/m6-level2-verify` @ `c6bf3f7`

**背景一句话：** CI 只在 push 到 `main` 或 PR 到 `main` 时触发
（[ci.yml](../../.github/workflows/ci.yml) 的 `on.push.branches: [main]`）—— **推发版
分支不产生任何 run，推 tag 也不产生**。复核对照的 **21 项**门禁/检查里，CI 实际跑
**14 项**，**6 道只存在于本地**（§8.1）；另有 **6 类改动，改了不会被任何自动化发现**
（§8.2）。这两块恰好是 v1.0.0 这一版发版质量里最要紧、也最没有兜底的部分，所以本节
把它们写成**发版前逐条打勾的动作**，而不是「有余力再做」的建议。

### 8.1 本地跑、CI 不跑的 6 道门禁

| # | 门禁 | 命令 / 文件 | 漏掉会怎样 |
|---|---|---|---|
| L1 | 完整测量 | [refresh-report-figures.py](../../scripts/refresh-report-figures.py) | 报告与 README 徽章里的 1,588 / 93.3% 停在最后一次本地测量 |
| L2 | 契约活检 | [verify-public-contracts.py](../../scripts/verify-public-contracts.py) | 活检判定逻辑改坏无人发现；契约表 §7 的实跑记录一直是旧的 |
| L3 | M10 自查 | [m10_selfcheck.py](../../scripts/m10_selfcheck.py) | [m10-selfcheck.md](m10-selfcheck.md) 的手写快照与脚本当前行为脱节 |
| L4 | 对外素材点检 | [outreach-publish-checklist.md](outreach-publish-checklist.md) | 对外素材里的数字与本仓库脱节 |
| L5 | Release 附录行号重锚 | [v1.0.0-github-release-body.md](v1.0.0-github-release-body.md) 末尾出处表 | 附录指向的行不再写它声称的内容 |

  `<!--fig:tests.total-->1612<!--/fig-->`），而不是空标记或占位文本；

  coverage 两个徽章数字同步更新；再 `uv run --no-sync pytest tests/test_docs.py -q`

  **出问题怎么办**：中途若跑过子集测试（`.coverage` 已被顶掉），必须**重跑完整测量**，

#### L2 契约活检（CI 对这个脚本零引用）

  **出问题怎么办**：分母变了要**重跑完整测量**再更新文档里的期望输出（§7 N1），不要
  只改文档里的数字。

### 8.2 「改了不会被任何自动化发现」—— 发版前人工过一遍

判定标准：**这个仓库里没有任何脚本、测试或 workflow 会因为它变红**。下面 6 类是复核
认定「不该没人却没人」的（复核报告 §4 的 4.1–4.6）；另两类是设计使然，见 §8.3。
这一节是**按改动类型**的视角，与 §8.1 的**按门禁**视角互补：两条都过，才算把发版
质量里没有自动化兜底的那一半补上。

| # | 改了什么 | 主要涉及文件 | 谁会响 |
|---|---|---|---|
| B1 | 对外素材里的测量数字 | `docs/outreach/`、`docs/case-studies/`、`docs/proposals/` | **没有人**（靠 L4 的人工清单） |
| B2 | Release 附录里的 `文件:行` | `docs/reports/v1.0.0-github-release-body.md` | **没有人**（靠 L5 的手工重锚） |
| B3 | how-to-verify 的示例输出 | `docs/how-to-verify.md` | **没有人**（靠 L6 的人工实跑） |
| B4 | 契约活检的实跑结果 / 静态 49 条 | `scripts/verify-public-contracts.py`、`docs/architecture/public-contracts.md`、Release 正文 | **没有人**（L2 只查活检本身，不查各处说法是否一致） |
| B5 | M10 自查快照 | `scripts/m10_selfcheck.py`、`docs/reports/m10-selfcheck.md` | **没有人**（靠 L3 的重跑重写） |
| B6 | 源指纹覆盖不到的改动 | `scripts/` 下除测量脚本外的全部、`docs/`、README | **没有人**（指纹不动，断言照样绿） |

- [ ] **检查项（B1）**：对外素材里的数字是否仍与仓库一致 —— 走 L4 的清单，
  一条一条打勾，不抽查。
  **出问题怎么办**：任何一处不一致，先改素材，不要改报告。

- [ ] **检查项（B2）**：Release 附录的 30 余条出处是否仍指向声称的内容 —— 走 L5 的
  手工重锚。**按内容定位，不按行号推算。**

- [ ] **检查项（B3）**：how-to-verify 的期望输出是否仍等于实跑输出 —— 走 L6 的实跑比对。

- [ ] **检查项（B4）**：契约活检的**三处记录必须说同一件事**。
  **怎么查**：核对三处 —— ① [v1.0.0-github-release-body.md](v1.0.0-github-release-body.md)
  的 **M8 正文段落**；② 同一文件末尾出处表里「契约活检」那一行；③
  [public-contracts.md](../architecture/public-contracts.md) §7 的两张实跑表。
  三处必须出自**同一次**实跑，且退出码一致。
  **复核基线上的实况（发版前必须消掉）**：①②③ 不一致 —— M8 正文段落仍写着
  "the all-backends run executes 48 and ends with **46 passing and exit 1**"（脚本修复
  前的那次），而 ② 与 ③ 已经是修复后的 **48/48、退出码 0**。**读者拿到两份说法相反的
  记录，而 CI 全绿、没有任何自动化会响。** 若该处已被修正，本项只剩「确认三处一致」。
  **出问题怎么办**：以**契约表 §7 与脚本当前实跑**为准（这两处同源），把正文段落改过来；
  不要反过来改契约表去迁就旧正文。

- [ ] **检查项（B5）**：M10 自查快照是否还等于脚本当前输出 —— 走 L3 的实跑比对。

- [ ] **检查项（B6）**：本轮改动里凡是改了**源指纹覆盖不到的东西**，都要自己判断
  「报告数字是否还成立」。
  **怎么查**：源指纹覆盖 `src/dexatlas/**/*.py` + `tests/**/*.py` + `pyproject.toml` +
  `scripts/refresh-report-figures.py` —— **不覆盖** `scripts/` 下其它脚本、`docs/`、
  `README.md` / `README.zh-CN.md`、`examples/`。所以当
  `git diff --stat <基线> -- src/ tests/` 为空、而
  `git diff --stat <基线> -- scripts/ docs/ README.md README.zh-CN.md` 不为空时，
  **报告里的 1,588 / 93.3% 依然「新鲜」**，指纹断言照样绿 —— 但那只说明 `src/` 与
  `tests/` 没动。要另外处理的是：
  - 改了 `scripts/verify-public-contracts.py` 或 `scripts/m10_selfcheck.py` → 走 L2 / L3；
  - 改了 `scripts/refresh-report-figures.py` 本身 → 指纹**会**变（它在 `FINGERPRINT_FILES`
    里），此时必须重跑完整测量（L1）；
  - 改了 `docs/` 或 README → 报告数字仍然新鲜，但要按 B1–B5 逐条核对外材料。
  **出问题怎么办**：不要拿「指纹没变」推断「文档也没错」—— 指纹只回答「代码还是同一份
  代码吗」。

### 8.3 按设计就该没有自动化的两类（不要试图自动化）

复核报告也把这两类列进「改了不会被发现」，但明确写了它们**不是缺陷**，因此不列入
§8.2 的检查项：

- **40 项人工验收判定**（[m10-acceptance-pack.md](m10-acceptance-pack.md)）：
  `scripts/m10_selfcheck.py` 把它们标成 `manual`，而 `manual` **不算失败**。它们本来就
  该由一位未参与实现的读者在真实机器上执行，并填入
  [m10-review-record-template.md](m10-review-record-template.md)。
- **发送前的占位符与人工判断**：[cover-letter-templates.md](../outreach/cover-letter-templates.md)
  里的 `{{...}}` 槽位与 [m10-invitation-sender-checklist.md](m10-invitation-sender-checklist.md)
  里的「由你决定」—— **模板态是合法的仓库态**，自动化去检查「占位符是否被替换」与
  「发布前最后点检」原则上冲突。

### 8.4 候选清单：要不要加进 CI —— 由作者决定

复核报告给了 11 条建议。**本节只列清单，不代改**；`.github/workflows/` 这次**没有动**。
要不要做、什么时候做，**由作者决定**。加之前先想清楚一件事：CI 只在 push/PR 到
`main` 时触发（推 tag 不触发），所以**每加一条 CI 门禁，都要同时决定它在什么事件下
会被跑到** —— 否则只是把「本地独有」换成「只在一处触发」。

| # | 候选 | 改哪里 | 为什么 |
|---|---|---|---|
| C1 | 加 tag 触发 | `ci.yml` 的 `on.push` 加 `tags: ['v*']` | 重打 tag 现在不产生任何 run，tag 指向错了永远没人知道 |
| C2 | 放宽 `on.push.branches` | 去掉 `[main]` 过滤，或至少加 `claude/**` 与发版分支 | 推发版分支现在完全没有 CI 兜底 |
| C3 | 调 `concurrency.cancel-in-progress` | 对 `main` 设为 `false`，或取消时保留前一次结论 | 连续两次推 `main`，前一次（含发版 commit）的验证结果被静默丢弃 |
| C4 | 扩 `DOCS` 列表 | `scripts/check-doc-citations.py` 的 `DOCS` 加 `docs/releases/*.md` 与 `docs/reports/v1.0.0-github-release-body.md` | Release 附录的 30 余条行号出处从不被核对（B2） |
| C5 | 活检进 CI | 新 job 跑 `scripts/verify-public-contracts.py`（需三后端，可挂在 3.12 的 `test` job） | 契约活检的实跑结果没有任何自动化守护（B4） |
| C6 | 自查进 CI | 新 job 跑 `scripts/m10_selfcheck.py`（只读、退出码可判、零成本） | 自查快照会与脚本脱节（B5） |
| C7 | 测量 `--check` 进 CI | 新 job 跑 `scripts/refresh-report-figures.py --check`（只比较不写入），至少挂 tag 触发 | 完整测量目前纯本地（L1） |
| C8 | 扩大源指纹 | 把 `verify-public-contracts.py` 与 `m10_selfcheck.py` 纳入指纹，或在报告与 README 里显式写明「指纹不覆盖这两个脚本」 | 改它们不影响指纹（B6） |
| C9 | 扩版本声明检查到对外素材 | `scripts/check-version-claims.py` 的 measured-numbers 规则覆盖 `docs/outreach/`、`docs/case-studies/`、`docs/proposals/` 的覆盖率、测试数、样本数 | 素材数字现在零自动化（B1） |
| C10 | how-to-verify 输出核对 | 为 `pytest --collect-only` 的分母与两段分类数建立比对 | 文档给读者的期望输出没有任何东西比对（B3） |
| C11 | 「静态 49 条」加断言 | 在 `tests/test_public_contracts.py` 或活检脚本里断言 `check()` 调用点数与文档复述的数一致 | 这是为少改 5 处材料而维持的人工耦合不变量（B4） |

**本节与 §1–§6 的关系：** §8 不新增发版动作，它把「本地门禁」与「没有自动化的改动」
变成**可核对的清单**。发版前按 §3 走完流程 → 按 §7 勾八条 → **按 §8.1 勾六道本地门禁、
按 §8.2 勾六类盲区** → 按 §5 处理阻断项与披露项 → 按 §6 由作者决定。§8.4 的候选清单
是**给作者的决定项**，不是发版前的必做项。
