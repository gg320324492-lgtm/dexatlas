## 3. 发版流程步骤

每步附命令与核对方法。凡涉及生成数字的步骤，完成后不得再改 `src/`、`tests/`、
`benchmarks/`；改了就回到步骤 3 重测，否则报告描述的树与发布树不一致。

### 步骤 1：版本号定稿

- [ ] `src/dexatlas/__init__.py:11` 的 `__version__` 改为 `"1.0.0"`。pyproject 经
  hatch 从该文件读版本（`pyproject.toml:146-147`），无需改 pyproject。
- [ ] `CHANGELOG.md` 的 `## [Unreleased]` 改题为 `## [1.0.0] — <发布日期>`；文末
  compare 链接新增一行 `[1.0.0]: https://github.com/.../compare/v0.2.0...v1.0.0`。
- 核对：`uv run --no-sync dexatlas version` 输出 `1.0.0`；
  `uv run --no-sync python scripts/check-version-claims.py --base auto` 通过。

### 步骤 2：全门禁

```bash
uv run --no-sync ruff check . && uv run --no-sync ruff format --check .
uv run --no-sync mypy
uv run --no-sync vulture src/ tests/ scripts/ benchmarks/ --min-confidence 80
uv run --no-sync pytest -q
uv run --no-sync python scripts/check-doc-citations.py
uv run --no-sync python scripts/check-version-claims.py --base auto
```

- [ ] 全部通过。**跳过不是通过**：读 pytest 汇总行的 skip 数，必须为 0。
- [ ] 建议补跑 CI 的本地对应：Python 3.12 全后端、3.13 无外部后端、
  仅 Apktool、Docker 构建、依赖审计（`uv run --no-sync pytest` 覆盖前三个）。
- [ ] CI 侧确认：当前 CI 共 **9 个 job / 10 次并行运行**（`lint`、`test` 矩阵两个
  Python 版本、`test-partial-backends`、`m3-comparison`、`docker`、`security`、
  `contracts`、`m10-selfcheck`、`measurement`），触发条件是
  `branches: [main, 'release/**']` 与 `tags: ['v*']`（[ci.yml](../../.github/workflows/ci.yml)）。
  核对：`gh run list --branch main --limit 1`（发 tag 后用
  `gh run list --branch v1.0.0 --limit 1`），确认最新一条的 conclusion 是 success
  且 headSha 是要发布的那个 commit。**推 tag 会产生 run，但重打 tag 会取消前一次
  的 run**（见 §3 步骤 8）。

### 步骤 3：完整重测量（让数字属于发布 commit）

前提：三个后端可用、fixtures 已取、Pillow 与 ffmpeg 在、全部 git tag 在本机；
本机 `.venv` 含全部 extras（`uv sync --extra dev --extra analysis --extra mcp

**不要与其他会话/窗口并发执行**——并发会互相清 `.coverage`，把残缺覆盖率写进报告
（本项目已踩过）。

```bash

uv run --no-sync python scripts/refresh-report-figures.py
```

- [ ] `refresh-report-figures.py` 实际写入了数字（测量不完整时脚本会拒绝写入并保留
  旧值——此时不得手改，必须补齐前提后重跑）。
- [ ] **步骤 3 之前先按当前树的 collect 输出更新
  [`how-to-verify.md`](../how-to-verify.md) 与 [`how-to-verify.zh-CN.md`](../how-to-verify.zh-CN.md)

  不通过自己的测试** → 测量脚本按纪律**拒绝写入任何数字**（2026-11-18 实际撞过两次）。
  于是形成闭环：数字要等测量落盘才准，而测量要等数字对了才肯落盘。**先改那两页，

### 步骤 8：发布后修正并重打 tag（发布之后才发现错时的路径）

> **触发条件**：发布后发现数字、引用、契约说法或 Release 正文有错；或发现要改的东西
> 会改变测量结果（改了 `src/`、`tests/`、`pyproject.toml`、或
> `scripts/refresh-report-figures.py`）。
>
> **顺序不可换位**：
> 1. 改代码 → `ruff format` → **完整重测量**（§3 步骤 3；数字变了才需要）；
> 2. 改文档里的数字与引用（按内容重锚，不按行号推算）；
> 3. 提交（提交信息写清「修正了什么」）；
> 4. **重打 tag**：`git tag -f -a v1.0.0 <新的 commit> -m "<主题>"` +
>    `git push --force origin v1.0.0`；
> 5. **等新的 CI run 变绿**（旧 run 已作废：`gh run list --branch v1.0.0 --limit 1`
>    的最新一条 `headSha` 必须等于新 tag 指向的 commit，conclusion 必须是 success）；
> 6. **重跑 §7 N6 的同源核对**，且这次要核对**四份**（含 GitHub 上已发布的那一份）；
> 7. 若正文变了：`gh release edit v1.0.0 --notes-file .scratch/release-body.md`，
>    然后重新 diff 一遍。
>
> **判据（四条同时成立）**：
> - `git rev-parse v1.0.0^{commit}` == `origin/main`；
> - tag 的 CI 最新一条 run 的 conclusion == success 且 headSha == 上述 commit；
> - 四份对外文本的同一批数字集合相等；
> - GitHub Release 页上显示的正文与仓库里的正文文件逐字一致。
>
> **谁看 CI**：这一步没有任何自动化守门——发版者必须自己盯到 run 结束。
> 「推完 tag 就去写文档」是 v1.0.0 最后一次 tag 变红的直接原因。
>
> **这条路径的来源**：[release-process-dry-run.md](release-process-dry-run.md) §8：
> v1.0.0 的 tag 在 Release 发布之后被重打过 5 次，每一次都让上一次的 CI 结论作废，
> 而当时的清单里**一个字都没有**这条路径。

## 7. 追加检查项 —— 这一轮实际踩到的坑

**补记日期：** 2026-11-17 · **补记基线：** `8524503`（分支
`claude/release-checklist-lessons-7b9767`）。

§1–§6 是发版的**流程**；下面八条是 v1.0.0 这一轮真实踩到、并且**已经改进过代码**
的地方——规则本身已经写进脚本、判据与文档，这里记的是「怎么确认它还成立」。每条
给出**怎么查**与**出问题怎么办**。§1–§6 不因此重排。

### N1 测量必须独占

- [ ] **检查项**：同一个 checkout 里不能并发跑测量。
  `scripts/refresh-report-figures.py` 给每次测量用**私有**的覆盖率数据文件
  （`measurement_data_file()` → `.scratch/coverage/<pid>/.coverage`，目录常量
  `MEASUREMENT_DATA_DIR`），并用环境变量 `COVERAGE_FILE` 通知它启动的每一个进程
  （`measurement_env()`；配合 `COVERAGE_RC` 的 `COVERAGE_PROCESS_START` 与
  `parallel = true` 才覆盖得到 worker 子进程）。同一 checkout 的并发测量由
  `.scratch/measure.lock` 的**操作系统级文件锁**挡住（`try_measurement_slot()`）：
  已有测量在跑时新测量直接拒绝并打印说明，不与对方抢报告——锁只在「写这份 checkout
  的报告」时取，随进程结束由操作系统释放。
  **怎么查**：`git worktree list` 看本机还有哪些工作树在跑东西；测量前后确认
  `.scratch/coverage/` 下只有本次运行的目录；再**问一句**同机器上有没有别的会话正
  在跑测量（锁挡得住同一 checkout，挡不住另一个会话同时改同一份文档）。
  **出问题怎么办**：等当前测量结束再跑，不要删锁文件；测量在跑时不要改任何会被它
  写进报告的文档——数字会在测量过程中漂。

### N2 不要用不带 `--cov-append` 的 `pytest --cov`

- [ ] **检查项**：改文档、跑子集测试时，`pytest --cov` 必须带 `--cov-append`。
  不带的话它把 checkout 根目录的 `.coverage` **整体替换**，并发时把正在跑的测量顶成
  残缺值——套件计数仍然正确、覆盖率却被换成一小撮覆盖面，报告与 README 徽章因此
  写出不实的数字（这一轮就发生过，规则已记进 CHANGELOG）。测量脚本自己的两个自检
  阶段用的正是 `pytest --cov=dexatlas --cov-append`（`measure_report_checks()` /
  `measure_status_checks()`）。
  **怎么查**：跑子集前先看命令行里有没有 `--cov-append`；没有干脆别跑 `--cov`
  （`uv run --no-sync pytest tests/test_docs.py`）；`.coverage` 已被 gitignore，
  要看它得用 `ls .coverage*`，不能靠 `git status`。
  **出问题怎么办**：`.coverage` 已被顶掉就必须**重跑完整测量**，不能只补跑一个子集
  ——报告的数字必须整份来自同一棵树。

### N3 报告数字落盘后才定稿

- [ ] **检查项**：测试数、覆盖率、徽章都由 `scripts/refresh-report-figures.py`
  生成，**顺序不可变**：改代码 → `ruff format` → 完整测量 → 再改引用这些数字的
  文档。格式化会移动行，报告记录的是源码树指纹，指纹在格式化之后就已经变了，所以
  格式化必须在测量之前；测量不完整（有 skip）时脚本拒绝写入并保留旧值。
  **怎么查**：核对 `docs/reports/phase1-execution-report.md` 里的 `<!--fig:...-->`
  **标记里面**的数字 == 最近一次完整测量的结果（标记保留，数字写在标记之内，不是把
  标记替换掉）；再跑 `uv run --no-sync pytest tests/test_docs.py`
  （`test_execution_report_coverage_figures_describe_the_current_code` 会核对记录里的
  指纹与当前树一致）。
  **出问题怎么办**：数字与文档不一致时改代码、**重跑测量**，不手改数字
  （CLAUDE.md 规则 3）；指纹对不上说明测量跑的不是现在这棵树，重跑而不是改数。

### N4 引用旧输出要用「」，反引号会被当成当前声明

- [ ] **检查项**：文档里**引用**别的文档或工具的旧输出（审计报告里的检查器输出、
  旧版自查结论、旧版本号）时，整段用项目的引述约定包起来：`「」`（也接受 `『』`、
  `“”`、`‘’`）。**反引号不构成引述**——它表示字面文本，会被
  `scripts/check-version-claims.py` 读成对**当前**状态的声明。
  **怎么查**：`uv run --no-sync python scripts/check-version-claims.py --base auto`，
  看是否有新增 finding；引用旧输出却没加引述的段落会在这里冒出来。
  **出问题怎么办**：把旧输出改成「」引述，或加「（历史记录）」之类的限定语；门禁
  指出的是一条真声明时改声明本身，不要改门禁去迁就它。

### N5 改动落地后统一重锚 `file:line`

- [ ] **检查项**：改过 `src/` 或任何被引用的文件之后，文档里的 `file:line` 锚点会漂。
  `scripts/check-doc-citations.py` 是权威；`scripts/remap-citations.py` 只在检查器说
  「符号已经离开被引用的行区间」时移动引用，且**幂等**（跑两次，第二次不改）。
  **跨文档引用要在所有改动落地后统一重锚一次**，不要边改边锚。
  **怎么查**：改动全部落地后依次跑

  ```bash
  uv run --no-sync python scripts/remap-citations.py
  uv run --no-sync python scripts/check-doc-citations.py
  ```

  并读检查器的输出（drifted 与 unresolved 都必须是 0）。remapper 默认处理检查器读的
  那 12 份文档（`scripts/check-doc-citations.py` 的 `DOCS` 列表：4 份固定文档 +
  `docs/releases/*.md` 全部 + Release 正文）；单份
  文档用 `uv run --no-sync python scripts/remap-citations.py docs/x.md`。
  **出问题怎么办**：remapper 修不了的是「指向地方而不是符号」的引用（它不猜），由
  人判断改成指向符号或改用文件级引用，再跑一次检查器确认。**注意机器够不着的地方**：
  Release 正文附录指向发版说明行号的引用（如 `docs/releases/v1.0.0.md`）不在检查器
  的四份文档里，漂了不会被报出来——那类引用只能人工重锚。

### N6 四份对外文本要同源对齐

- [ ] **检查项**：同一批对外数字出现在**四处**：`CHANGELOG.md` 的版本段、仓库内发版说明
  `docs/releases/v1.0.0.md`、GitHub Release 正文
  `docs/reports/v1.0.0-github-release-body.md`、以及 **GitHub 上已经发布的那一份正文**
  （**第四份不在仓库里，没有任何东西比对它**）。四处必须**同源**；本轮的一致性复核
  （`docs/reports/release-notes-consistency.md`）列出了九处「一边有、一边无」的口径
  差异，其中两处会让读者直接误判（独立验收的边界只在一侧、验证数字只在另一侧）。
  **怎么查**：逐条对照四份文本的同一批数字（套件计数、覆盖率、层级 2 逐轮分数、
  源码指纹），把复核报告列出的差异列表逐项过一遍；每个数字都能在落盘报告里找到
  出处（`docs/benchmarks/m6-level2-retest4.md`、
  `docs/reports/phase1-execution-report.md`）。第四份要单独看：
  `gh release view v1.0.0` 取出页面上显示的正文，与仓库里的正文文件 `diff` 一遍
  （[release-process-dry-run.md](release-process-dry-run.md) §4.4 实测这两份逐行一致）。
  **出问题怎么办**：**以落盘报告为准**修正文本，发版说明与 Release 正文谁跟
  报告对不上就改谁；CHANGELOG 的版本段随之同步。四份对齐之后再发 Release，别先发
  再补。

### N7 自查脚本的判据不能写死版本名

- [ ] **检查项**：给自查脚本加判据时，判据跟着「**最新一节**」和语义走，不写死版本
  名或 `[Unreleased]` 字样。这一轮 `scripts/m10_selfcheck.py` 的判据写死了「CHANGELOG
  顶部要有 `[Unreleased]` 一节」；v1.0.0 发布后那一节被清空（Keep a Changelog 的正常
  形态），一棵**正确**的树被判红——那是判据过时，不是 CHANGELOG 的缺陷。判据已改为
  检查最新一节（发版前是 `[Unreleased]`，发版后是刚打 tag 的那一节），条目 id 相应
  改为 `DOC.changelog-newest-section`，判据表在 `docs/reports/m10-selfcheck.md`。
  **怎么查**：新增或修改判据时，在 `scripts/m10_selfcheck.py` 里搜判据文本，确认
  没有写死的版本号或 `[Unreleased]`；判据改了，自查报告里的判据表也要同步。
  **出问题怎么办**：先把「判据过时」和「文档真的错了」分开。正确的树被判红时改判据
  （并同步自查报告），不要改正确的文档去迎合判据。

### N8 对外材料的人设口吻会被读成真客户

- [ ] **检查项**：素材里的第一人称客户叙述会被读者读成**真实客户案例**。这一轮把

  [case-studies/README.md](../case-studies/README.md) 里点明**样本数与分析数的

  **怎么查**：`grep -rin "customer" docs/case-studies/ docs/outreach/` 应为空；对外
  素材里每处第一人称叙述都要能回答一句「读者会以为这是谁的案例」。
  **出问题怎么办**：要么换词（不写 "customer"），要么在素材里点明样本数与分析数的

## 8. 自动化覆盖与盲区 —— 哪些门禁 CI 跑、哪些跑不了

**补记日期：** 2026-11-17 · **来源：** [ci-gate-coverage.md](ci-gate-coverage.md)（只读
复核）· **复核基线：** `claude/m6-level2-verify` @ `c6bf3f7`

**背景一句话：** CI 在 push 到 `main` / `release/**`、PR 到 `main`、以及**推 `v*` tag**
时触发（[ci.yml](../../.github/workflows/ci.yml) 的
`on.push.branches: [main, 'release/**']` 与 `on.push.tags: ['v*']`）—— 推发版分支会
产生 run，**推 tag 也会产生 run；但重打同一个 tag 会取消前一次的 run**。复核对照的
**21 项**门禁/检查里，CI 实际跑 **14 项**，**6 道只存在于本地**（§8.1）；另有 **6 类
改动，改了不会被任何自动化发现**（§8.2）。这两块恰好是 v1.0.0 这一版发版质量里最要紧、
也最没有兜底的部分，所以本节把它们写成**发版前逐条打勾的动作**，而不是「有余力再做」
的建议。

**补记（2026-11-18）：** 上面的「CI 不跑」说的是 **2026-11-17 那次复核当时的状态**。
此后 CI 加了 `contracts`、`m10-selfcheck`、`measurement` 三个 job，也开始收 tag 触发，
所以本节的每道门禁后面都补了一行「CI 现状（2026-11-18）」——**清单描述的是哪一棵树，
必须写清楚**（这正是 [release-process-dry-run.md](release-process-dry-run.md) §7 指出的
那 16 处陈旧前提之一）。

### 8.1 六道需要单独盯的门禁（CI 现状：2026-11-18）

### 8.5 改了测量口径，数字要分两类同步

新增或删除 `tests/` 下的文件会改源指纹 → 套件数与覆盖率随之变 → **对外数字必须分
两类同步，不许只改一半**：

| 描述哪棵树 | 文档 | 数字怎么取 |
|---|---|---|
| **发布树**（v1.0.0 那次测量） | `docs/releases/v1.0.0.md`、`docs/reports/v1.0.0-github-release-body.md`、五份 M10 读者材料 | **保留发布时的数字** —— 它们描述的是那个被 tag 的树 |
| **当前树** | `docs/portfolio.md`、`docs/status.md` §1 快照、README 徽章、`docs/how-to-verify.md` 与 `.zh-CN.md`、`docs/outreach/` 素材 | **跟新测量走**（状态页与徽章由脚本自动刷新，其余要手改） |

判据只有一句：这段文字说的是「v1.0.0 发布时」还是「现在」——前者不动，后者跟新数。
两边各自核一遍：这类改动正是 §8.2 那一类「改了不会被任何自动化发现」的改动。
