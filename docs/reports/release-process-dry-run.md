| `docs/reports/m10-invitation-sender-checklist.md:123-127` | `git tag -f -a v1.0.0 <提交> -m "…"` 的具体命令 | 它是**邀请读者**用的清单，在另一个语境里；发版者不会去那儿找 |
| `docs/reports/m10-reader-walkthrough-2nd.md:212-224` | 记录了「tag 会重打，所以现在这句话还不是真的」 | 是**审计发现**，不是发版步骤 |
| 三个发版后提交自己的 commit message | 「tag 将重打指向最终树」 | **是事后写下的记录，不是事前可执行的步骤** |

**本轮 v1.0.0 的重打，实际是这么发生的**（从提交信息与 CI 记录反推）：改文档 →
重锚行号 → 重测量 → 提交 → 重打 tag → 等 CI → 改 GitHub 上的 Release 正文 → 再核对数字。
每一步都做对了，但**每一步都不在清单里**，而且第 4 步之后没有「等 CI 变绿」这一步 ——
所以最后一个 tag 的 run 至今是红的。

### 8.3 这条路径应该长什么样（补进清单的内容）

> **§3.8 发布后修正并重打 tag**
>
> **触发条件**：发布后发现数字、引用、契约说法或正文有错；或发现要改的东西会改变
> 测量结果（改了 `src/`/`tests/`/`pyproject.toml`）。
>
> **顺序（不可换位）**：
> 1. 改代码 → `ruff format` → **完整重测量**（数字变了才需要）；
> 2. 改文档里的数字与引用（按内容重锚，不按行号推算）；
> 3. 提交（提交信息写清「修正了什么」）；
> 4. **重打 tag**：`git tag -f -a v1.0.0 <新的 commit> -m "<主题>"` + `git push --force origin v1.0.0`；
> 5. **等新的 CI run 变绿**（旧 run 已作废，`gh run list --branch v1.0.0` 最新一条
>    的 `headSha` 必须等于新 tag 的 commit）；
> 6. **重打后必须重跑 §7 N6 的同源核对**，且这次要核对**四份**（含 GitHub 上已发布的那份）；
> 7. 若正文变了：`gh release edit v1.0.0 --notes-file <正文文件>`，然后重新 diff 一遍。
>
> **判据（四条同时成立）**：
> - `git rev-parse v1.0.0^{commit}` == `origin/main`；
> - tag 的 CI run 最新一条 conclusion == success 且 headSha == 上述 commit；
> - 四份对外文本的同一批数字集合相等；
> - 执行报告的 `source_fingerprint` == **要发布的那棵树**重算的指纹。
>
> **谁做**：作者（1–7 步）+ 一位读者复核第 6 步的四份同源。
> **注意**：第 5 步之前，**不要**把 Release 页上的 tag 当成已验证的。

### 8.4 顺带必须补的一条：**谁看 CI**

清单 §3 步骤 5 写「CI 在该 commit 上全绿后再进入步骤 6」，但没有写：

- CI 现在**会**在 tag 推送时产生 run（`tags: ['v*']`）；
- 重打 tag 会**取消**前一个 run（已实测：`cancelled`）；
- 所以「等 CI 变绿」这条判据在重打之后**必须重新等一次**，而清单没有这一步。

## 9. 「清单里最该补的三条」（按会让发版出事的后果排序）

1. **补「发布后修正并重打 tag」这条路径，并把对外文本从三份改成四份。**
   后果最重：v1.0.0 的 tag 在发布后被重打了多次，每次都作废了上一次的 CI 结论，
   最后一次的 run 至今是红的；而 GitHub 上读者看到的那份正文，是清单从不检查的第四份文本。
   补法见 §8.3（含顺序、判据、谁做、以及「重打后必须重等 CI」）。

2. **补「发布出去的那份要自己再验一遍」这一层。**
   清单所有判据都停在「仓库里这份树」。读者的入口是 GitHub Release：那个 tag 指向的
   commit、那份正文、那次 CI 的结论 —— 三样都不在仓库里，也没有任何一处把它们钉在一起。
   最小可用形式：一条命令，`gh release view v1.0.0` + `gh run list --branch v1.0.0` +
   `git rev-parse v1.0.0^{commit}`，三者对不上就停。

3. **把清单里已经过期的数字与前提更新，并给「元文档」加一道门。**
   现状：套件数 1,588 → 落盘值（见 [phase1-execution-report.md](phase1-execution-report.md):76 的
   `<!--fig:tests.total-->`）、MCP 10 → 11、CI 六/七 → **9 个 job 定义 / 10 次并行运行**、
   准备度 77.5% → 81.25%、「推 tag 不产生 run」→ 现在产生、§8.1 的三道门禁 → 已在 CI、
   §8.4 的 **11 条候选**里 **7 条已落地 + 1 条部分落地**、
   §5 的 B4/B5 → 已关闭。这些不是笔误，是**清单没有随仓库一起演化的证据**。
   更要紧的是：L4 用的旧数字 1,588 照做会**诱导人去改脚本生成的数字**。
   补法：把清单里的数字改成「指向落盘报告的 `file:line`」，而不是抄一份；再加一道门
   （候选 C9 的思路）：清单/验收包/自查快照里出现的每个数字，必须能在仓库里找到它的出处。
