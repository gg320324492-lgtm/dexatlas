# GitHub / Upwork 作品集准备度评估

日期：2026-11-15。评估基准：`752d10a` 的本地源码及已提交文档。
这是为个人作品集重新定义目标的人工评审，不是生产成熟度认证、客户调查或接单概率。
Phase 2 的验收结论保持有效；Phase 3 尚未实施、尚未验收。

## 1. 做到什么程度合适

目标是让潜在雇主或客户回答三个问题：你解决什么问题、为什么信任你的结果、交给你后会收到什么。
合适的停止点是一个范围清楚、能独立复现、能交付可核查结果的代表作。
不需要先做成覆盖 Android 逆向全部领域的平台，也不需要先取得星标、订单或社区规模。

| 场景 | 达标时访客能做到什么 | 建议验收方式 |
|---|---|---|
| GitHub 第一眼 | 看懂用途、作者贡献、适用范围与限制 | README 首屏有实际输出、短演示、案例和试用入口；由首次读者复述用途 |
| 技术深读 | 从结论追到样本、源码、工具版本与运行记录 | 案例中的关键结论逐条解析 locator；失败和未覆盖范围同样可见 |
| 独立试用 | 按文档完成一个完整流程，不靠作者补命令 | 干净环境试运行，保存环境、耗时、输出和卡点 |
| Upwork 评估 | 看懂服务输入、交付件、验收和排除项 | 英文服务说明配一套可下载交付样例，明确个人项目身份 |
| AI 能力判断 | 分清确定性分析、真实模型结果和 scripted 演示 | 已发布 benchmark 可重算，真实模型成功与失败均有记录 |

这是本项目的评审标准。平台依据仅用于内容组织：
[GitHub README 指南](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)
建议说明用途、价值和上手方式；
[Upwork 作品集指南](https://support.upwork.com/hc/en-us/articles/360016144974-How-to-enhance-your-freelancer-profile)
要求填写项目、角色、描述及技能，并建议精选相关成果。
这些页面没有给出下文的评分或商业成功承诺。

## 2. 当前完成度：GitHub 约 75%，Upwork 约 65%

评分等级：0＝未见证据；1＝初步证据；2＝局部可用、仍有实质缺口；
3＝在声明环境内有完整演示或复现记录；4＝在该维度的限定范围内经过评审并有边界验证。
4 不表示软件无缺陷。下表的分值、权重均为人工判断，可在复核后调整。

| 维度 | 分值 / 4 | GitHub 权重 | Upwork 权重 | 已读证据与扣分原因 |
|---|---:|---:|---:|---|
| 核心工程与证据链 | 4 | 30% | 20% | [Phase 2 计划](../roadmap/phase2-plan.md)、[M4 源码评审](m4-review.md)、`tests/test_evidence_invariants.py`、`tests/test_upload_isolation.py`；范围限于已验收能力 |
| 首次试用与复现 | 3 | 20% | 15% | [安装说明](../install.md)、[端到端实测](m4-e2e-run.md)、Docker 和 CI 已有；未见本轮独立首次用户完成安装的验收记录 |
| Agent 可用性与评测可信度 | 2 | 10% | 15% | [强预算报告](../benchmarks/comparison-stronger.md)、[M4 复验](m4-e2e-run.md)；有真实模型完成案例，但默认预算与开放问题仍有缺口，不能据此声称广泛优于基线 |
| 客户交付件与服务边界 | 2 | 10% | 25% | [案例](../case-studies/README.md)、报告导出和 [portfolio 文案](../portfolio.md)已有；尚缺面向客户的范围、验收、离线证据包完整样例 |
| 对外展示与个人贡献说明 | 3 | 25% | 15% | 双语 README、视频、架构图与案例已存在；[当前状态](../status.md)披露视频的 Agent 使用 scripted provider，展示文案和旧路线图仍需统一 |
| 独立使用验证 | 1 | 5% | 10% | 可见记录主要是项目自身演练与评审，未见独立读者复现及客户式验收记录；不推断项目没有外部用户 |

计算：每项贡献＝分值 ÷ 4 × 该平台权重，分别求和得到 **75% / 65%**；
两平台同等重要时，平均为 **70%**。只应用于这个目标，不可与旧的六维生产成熟度分数混用。
考虑人工判断误差，建议把结论理解为 GitHub 约 70–80%、Upwork 约 60–70%，不要精确到小数。

本次核验包括：阅读上述交付与验收记录；查看 `core/pipeline.py`、`tools/registry.py`
和 `agent/state.py` 的现状；从已提交强预算 trace 运行下列命令重算指标。
没有重新跑真实模型、全部后端、完整测试矩阵或调查 Upwork 岗位市场，因此不作当前全面质量认证。

## 3. 旧第三阶段是否足够

**方向有价值，但验收重点与个人作品集目标不完全相符。** 旧草案偏重插件、
多工作区、可观测性、原生分析和 SDK，能增加工程深度，却没有强制验收客户服务说明、
可直接审阅的交付样例以及首次用户体验。已有视频、案例、MCP 和 benchmark 也不应再当作从零建设。

旧草案还有过期前提：F8 已在 CI 中由 vulture 守门；所谓 stronger rerun 已落盘，
是同一 MiniMax 模型的预算与执行条件变化，不能称为不同强模型的对照。
它也不能证明默认预算下 Agent 已经可靠。

按旧草案全部完成且验收通过的假设，粗估 GitHub 可到约 85%、Upwork 约 80%，
但缺少对应交付物，不能算已经达到。这个预测没有逐项未来评分，仅说明投入方向的偏差。
**重写后的 Phase 3 以两平台分别达到至少 90% 为退出目标，预期约 90–95%；
实际分数必须由验收证据重评。**

100% 仅表示本表各维度在约定范围内都有充分证据，不表示拿到订单、成为安全专家或具备 SaaS 运营能力。
客户评价、报价能力、沟通、真实付费交付经历需要在接单后另行建立，不能用个人项目替代。

## 4. 建议的服务定位

优先展示 **Python Backend & Automation** 和 **Evidence-first AI / MCP Integration**；
以 Android 静态分析作为有深度的应用场景。限定范围的 APK 分析可作为第三种交付样例。
这是根据仓库能证明的能力提出的定位，不是岗位需求量或收入预测。

展示作者实际完成的集成、数据模型、证据校验、接口和测试；说明 JADX、Apktool、Androguard
是第三方引擎，说明 AI 辅助开发的实际使用和作者审核责任。不得虚构客户、收益、节省时间或漏洞发现。
