## 2. 为什么这道声明要等 v1.1.0

### 2.1 它是公共契约变更

清单的形状是**公共契约**的一部分：读者拿到 zip，先看 `manifest.json`，
再决定信不信里面的 `files`。加一个键、改一个键的含义，都是**清单的形状变了**，
而清单自己写着「形状变了，版本号就要动」
（`src/dexatlas/reports/evidence_package.py:47-49`）。

按项目自己的版本政策（`docs/architecture/public-contracts.md:342-347`），
「加字段」是**兼容**变更（CHANGELOG 说明即可），「改字段含义、删字段」才是破坏性变更。
**加第四个键落在哪一档，取决于它怎么加**：

- 若只是给 `not_included` **多一个并列的键**，其余三个键的含义一字不改，
  按政策可以只记 CHANGELOG；
- 但本项还**要动 `schema_version`**，而 `schema_version` 一动，**旧包在新代码下读不了**
  （见 §1.4）——这已经是破坏性变更，按政策要**升版本号并在 CHANGELOG 显式声明**。

**所以「要不要升 `schema_version`」不是口味问题，是一次要记账的决定**：
升，四个已入库的包在下游代码里读不了；不升，那四个键和 `schema_version = 1`
一起留在一个已经变过的形状里——**清单会说自己是什么形状，而它已经不是了**。

### 2.2 影响面远大于它覆盖的风险

这道声明覆盖的风险是「有人把打包器的输入根目录放宽一点」。
**而那条风险今天已经有闸了**（§1.5 的守卫 + 5 条红→绿测试），
执行侧的守卫**不依赖**清单里的一个字。换句话说：**这一层是给读者看的，不是给机器看的**——
它的价值是让读者打开包时知道边界在哪，而不是让边界成立。

代价却是实的：五个文件的九处、两个活材料的六处、四个已入库包的处置、
一次测量窗口。**为一句声明付这个代价，是排期上的取舍，不是紧急度上的取舍。**

### 2.3 但它也不能悄悄加

「不加就什么都不做」也不是选项：

- 清单是**读者判断这个包能不能信的依据**。清单少了一条声明，读者就少一条依据；
- 契约文档 §5.3 现在写着「包内只有本次分析」（`docs/architecture/public-contracts.md:324-327`），
  **而清单没有这句话**——两处对不上，读者核到清单那一处会看见一个没说法的清单；
- 项目规矩第 5 条：公共契约**要么保留、要么显式版本化**，不能悄悄改。

**所以它该被登记、被排期，而不是被忘掉。**

## 3. 加第四个键要动哪几处（逐条）

### 3.1 代码与契约

见 §1.2 的九处表格。补充三点：

1. **第四个键叫什么**：键集合是被断言的，键名一变，上面九处里有四处要跟着改。
   建议与现有三个键**同风格**（`apk` / `full_sources` / `unrelated_strings` 都是
   名词短语），例如 `outside_analysis`；文案要说清的是
   「**只有本次分析产出的文件进包**；工作区里别处的文件、以及指向别处的链接，都不进包」。
2. **清单的形状块**：`docs/architecture/public-contracts.md:316` 那行
   `not_included: {apk, full_sources, unrelated_strings}` 要跟着改
   （2026-11-20 C16 落地，已改为四键）；
   同一节的 `:333-334`（C16 落地后 `:337-339`；C8 重构后已改写，在 `:346-347`）那句「形状与 `schema_version = 1` 不变」要改成升版说明。
3. **读旧包的读者怎么办**：`src/dexatlas/reports/evidence_package.py:360-368`
   现在对版本不匹配一律报错。升到 2 之后，**旧包会读不了**。
   要么改成「接受 1 与 2，但 1 缺一条声明」（那就得在读的地方补一句说明），
   要么保持严格（那就得接受旧包读不了，并写进材料）。**这一条要在动工前定。**

### 3.2 验收材料

见 §1.3 的活材料六处。M10 验收准备包是**交给外部读者执行的判据**，
它的 D3 与 G5 两项（`:128` / `:166`）是**星级检查**——读者照着判，
所以它们必须与新清单一致，否则读者会拿旧判据判新包。

### 3.3 顺带要定的三件事

| # | 要定的事 | 为什么它与这一项绑在一起 |
|---|---|---|
| 1 | 第四个键的**键名与文案** | 键集合被四处断言，名字定了才写得下去 |
| 2 | 旧包（`schema_version = 1`）**读不读得** | 决定 §3.1 第 3 点怎么写，也决定四个已入库的包要不要重打 |
| 3 | 四个已入库的包**重打还是保留** | 保留 → 案例研究里的 sha256 不变，但要写明它们是旧形状的产物；重打 → 案例研究与走查记录里的哈希要跟着更新 |

### 3.4 怎么算做完（可运行的检查）

改完之后，这三道要绿：

1. `uv run --no-sync python scripts/m10_selfcheck.py` 的 `D3.not-included` 判**过**
   （阻塞级；脚本里的 `expected` 集合改成四键后，必须仍与源码一致——不一致就判红）；
2. `uv run --no-sync pytest tests/test_public_contracts.py::test_the_evidence_package_manifest_is_versioned tests/test_evidence_package.py -q`
   全绿——那条测试同时断言 `PACKAGE_SCHEMA_VERSION == 2` 与四键集合；
3. 新导出的一个包里，`manifest.json` 的 `not_included` 有**四个**键、`schema_version`
   是 **2**（一条 `python -c` 读 zip 就能读出来）；
4. `uv run --no-sync python scripts/check-doc-citations.py` 报 `drifted: 0`
   （契约文档 §5.3 的形状块改了行号，要重锚）。

### 3.5 估时与依据

**半天到一天（0.5–1 个工程日）**，不含重打已入库的包。

- **工程日刻度**：Phase 3 计划里 M10 本身是 3–4 个工程日
  （`docs/roadmap/phase3-plan.md:79`）。本项只做「清单声明这一层」——
  一个常量、一个键、两个测试文件、一个自检脚本、一份契约文档、两份活材料——
  约是 M10 的三分之一。
- **若连带重打四个已入库的包**：分析本身是秒级的（首次分析实测 3.8 秒，
  `docs/reports/reader-dry-run.md:53`），成本在**重新分析 + 更新案例研究里的
  sha256 + 复跑对比**，另加约 **1 个工程日**。

> 两把尺子的出处见 v1.1.0 候选清单 §1.2；这里的数字是**量级**，不是承诺，也不是报价依据。

## 4. 不改会怎样

**今天不改，什么都不会坏**——因为守卫在，性质成立着。代价是这四条：

1. **清单少一条声明**：读者打开 `manifest.json`，看到的三个键说的都是「少带了什么」，
   没有一条说「包里只有本次分析」。要自己推断。
2. **契约文档与清单对不上**：§5.3 明写「包内只有本次分析」
   （`docs/architecture/public-contracts.md:324-327`），清单里没有这句话。
   读者核到清单，会看见一个**没说过这句话的清单**。
3. **守卫是唯一的一道闸**：今天的边界由
   `src/dexatlas/reports/evidence_package.py:291-314` 一个函数撑着。
   哪天有人为了「顺手把评审记录一起发过去」把输入根目录放宽一点，
   改动**不在清单里**、**不在契约文档里**，所以**没有任何一道声明会响**——
   只有测试会红。这就是「只靠实现细节成立」的意思。
4. **升级路径会被推迟**：清单的形状越长越没人敢动。三个键用了几个版本，
   第四个键要拖到什么时候就得看拖到什么时候。

**换个说法**：不改是安全的，**拖着不改是贵的**——贵的不是风险，是**升级的把握**。

  `publish-review.md` 这个内部核对记录）；
