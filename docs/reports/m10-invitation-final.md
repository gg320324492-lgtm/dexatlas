### 一、我们邀请您做什么

DexAtlas 已完成从安装到交付样例的开发，进入 v1.0.0 的候选验收阶段：
**独立验收**。我们想请您以一位从未参与开发的真实读者的身份，回答一个问题：

> **一个不认识我们的人，能不能只靠仓库里的文档，把 DexAtlas 装起来、
> 跑通一个完整分析案例，并核对报告里的结论确实能追溯到代码？**

具体包括三部分：

1. **首次读者路线**：从 `git clone` 开始，完成推荐安装路线，对一个演示 APK
   做一次完整分析，导出报告与证据包（验收项 A、B、D 组）。
2. **客户视角审阅**：不安装也能做的部分——阅读三个交付案例，判断
   「输入与结论是否清楚」「引用能否核查」「事实与线索能否区分」（C、D 组）。
3. **评分**：按既有的六维度、双平台权重（GitHub / Upwork）重新打分，
   每项附扣分理由（空白表见[验收准备包 §5](m10-acceptance-pack.md)）。

完整的 **40 项检查表**（含 19 项一票否决的阻断项）见
[验收准备包](m10-acceptance-pack.md)。**您只需要逐项给出
「通过 / 不通过 / 未验证」三态判定之一，没有「大概可以」。**

**关于项目现状，我们如实告知**：Agent 能力层级 2（真实模型）的多轮验证
均未达到项目自设的验收线（最终完整重测 DexAtlas 49/60 = 81.7%，逐轮
17/15/17，低于「每轮 ≥80%、三轮合计 ≥90%」），连续三轮窄验证也未达判据后，
项目已按既定验收方案停止投入，将 Agent 服务定稿为**现状披露**——即
「有界、证据可核查的 agent 演练」，不宣称达到验收线。这是您在评审中
会重点核对的高风险声明之一（见[读者验收包 §4](m10-reader-package.md)）。

### 三、您需要准备什么

| 项目 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows 11 或 Linux | 两者有实测记录；**macOS 未验证**，如使用请如实记录 |
| Python | 3.12 或 3.13 | 项目 CI 在两个版本上运行 |
| [uv](https://docs.astral.sh/uv/) | 最新版 | Python 包与环境管理器；安装方式见[其官方文档](https://docs.astral.sh/uv/getting-started/installation/) |
| JDK | 21+（可选） | 仅 JADX / Apktool 后端需要；没有 Java 也能用 Androguard 完成基础分析 |
| Docker（可选） | 稳定版 | 不想装 Python/JDK 时走 Docker 隔离路线 |
| `gh` CLI（可选） | 仅拉取 fixtures 时需要 | `scripts/fetch-fixtures.sh` 经 GitHub API 拉取 androguard 测试数据 |
| 网络 | 首次需要 | clone、依赖与后端下载；装好后分析本身可离线 |
| 磁盘 | 预留数 GB | 依赖、后端与分析产物；不要写到系统盘根目录 |
| 时间 | 首次复现 10–20 分钟；完整验收预留半天 | 冷缓存（含 clone、依赖、后端下载）首次 10–20 分钟；暖缓存（JDK/uv 已就绪）到第一份报告约 1.5–2 分钟；完整案例约 1–2 分钟；40 项判定加两平台打分视抽查深度而定 |

JADX 与 Apktool 是可选的第三方后端，不是本仓库依赖：没有它们，分析仍然
完成，只是报告中会写明哪些步骤未运行（这本身就是一项验收内容）。获取方式
写在 [docs/install.md](../install.md)。

### 四、执行路径

完整分步命令、每步预期输出与记录格式，以
[读者验收包 §3](m10-reader-package.md) 为准；此处是路径概览：

1. **clone 并检出固定 commit**：按[读者验收包 §3.1](m10-reader-package.md)
   执行 `git clone` 与 `git checkout 277d0fa`，`git status` 应为干净。
2. **环境准备**：按[读者验收包 §3.2](m10-reader-package.md) 执行
   `uv sync --extra dev --extra analysis --extra mcp --extra demo`
   （或 Docker 路线），运行 `uv run dexatlas backends` 确认后端状态。
   没有外部后端不要停，这本身是验收项 A6 / G2 的降级场景。
3. **首次分析**：按[读者验收包 §3.3](m10-reader-package.md) 对
   `examples/demo-app/demo.apk` 执行 `uv run dexatlas analyze`，
   记录实际计数（预期 5 classes / 8 methods / 23 call sites /
   21 call edges / 1 resource string；不同先核对后端是否齐全）。
4. **案例与证据核查**：按[读者验收包 §3.4–3.7](m10-reader-package.md)
   执行 manifest / search / source / xrefs、三格式报告导出、证据包导出与
   校验，并任选 3 条 evidence 记录核对工具、版本、locator、level 四字段。
5. **源码评审（如您承担该角色）**：按
   [验收准备包 §6 源码评审清单](m10-acceptance-pack.md)逐里程碑核对
   M5–M9 的证据入口与核对动作；没有执行的动作记「未验证」。
6. **逐项判定**：对照
   [验收准备包 §2 的 40 项检查表](m10-acceptance-pack.md)逐项给出
   三态判定；每项写明命令、退出码、关键输出、耗时与路径。
7. **打分**：按[验收准备包 §5 的空白评分表](m10-acceptance-pack.md)
   给 GitHub / Upwork 两套权重分别打分，每项附扣分理由；两个平台
   **分别** ≥90% 才算达到评分目标，平均分不能替代，且分数不能抵消
   阻断缺陷。
8. **填写并交回记录**：把上述过程填入
   [验收记录模板](m10-review-record-template.md)，按
   [读者验收包 §5.3 的提交格式](m10-reader-package.md)交回发起人。

### 八、独立性要求

为使结论可信，请您遵守：

1. **未参与实现**：您没有为本项目写过代码、文档或做过评审。如曾参与，
   请如实告知，发起人会另行安排。
2. **不采信作者自述**：README、案例、报告中的每个数字，要么由您重跑命令
   复现，要么记「未验证」。作者的解释只能作为线索，不能作为证据。
3. **作者不补步骤**：发起人可以澄清名词含义，但不替您补命令、改环境或
   远程操作您的机器。凡是靠发起人口头补充才走通的步骤，相关验收项判
   不通过。
4. **固定 commit**：全程只验 `277d0fa` 这一个提交，所有记录写明 hash。
5. **如实记录**：预期输出与实际输出不一致时，以实际输出为准，把差异写成
   卡点；文档缺步骤本身就是缺陷，不要替项目圆场。
