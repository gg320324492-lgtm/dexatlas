> `${{ github.workflow }}-${{ github.ref }}`（[ci.yml:23](../../.github/workflows/ci.yml)），

> （[ci.yml:32](../../.github/workflows/ci.yml)）——**正在跑的 run 不会被这个设置打断**，

> `cancelled`。GitHub 的只读 API **不提供「被谁取消」的字段**，所以取消的**原因**

## 4. 这几次 run 说明了什么

### 4.1 重打 tag 会作废前一次 run 的结论

`v1.0.0` 这个 ref 一共推了 6 次，每一次都让上一次的结论作废：

- 第 2 次重打（run `44111034946`，绿）让第 1 次（run `44107083396`，绿）的结论作废；
- 第 4 次重打让第 3 次的**红**结论作废；
- 第 5 次重打让第 4 次（run `44126696597`）在 0 个 job 的状态下记为 `cancelled`。

run `44126696597` 是这条路径最干净的一次证据：**它一个 job 都没跑**，所以它的
「结论」里没有任何可读的东西。**读 `gh run list` 的最新一条，读到的永远是最新一次
推送的结论，不是「这个发布版本」历史上任何一次别的结论。**

### 4.2 前三次绿、后两次红（本文落笔时的前六次）

| 次数 | 结论 |
|---|---|
| 第 0 次（原始 tag） | 绿 |
| 第 1 次重打 | 绿 |
| 第 2 次重打 | 绿 |
| 第 3 次重打 | **红**（3 条断言） |
| 第 4 次重打 | 取消（0 个 job） |
| 第 5 次重打 | **红**（1 条断言） |
| 第 6–13 次重打 | 见 §3.7 |
| 第 14 次重打（当前 tag） | **绿**（14 个 job 全绿） |

第 0 次（`14:30:12Z`）在 Release 发布（`14:45:39Z`）**之前**，第 1、2 次在发布之后
**25 分钟内**；红的那两次都在发布之后**一小时以上**。

但要把「发布」和「tag 指向哪棵树」分开看：**发布出去的正文并不停在第 1 次重打的那
棵树上**。Release 对象的 `published_at` 是 `14:45:39Z`，`created_at` 是 `16:32:33Z`
（= 最后一次打 tag 的时刻）；发布页上现在显示的正文引用源指纹 `sha256:975afa8e…`，
与**记录当时** tag 指向的那棵树（`75976e0c`）里的指纹一致。

所以真正的差距不是「正文与树对不上」，而是：

> **发布出去的正文已经对齐到当前树，而当前树自己的 CI 结论是红的。**
> 正文说的与代码说的对得上，但这棵树没有通过它自己的测试。

### 4.3 红的根因：最后一条是同一条契约判据

第 5 次重打（当前 tag）的红由**一条**断言造成，在 4 个红 job 里各出现一次：

```
tests/test_public_contracts.py::test_every_document_that_states_the_check_count_states_the_right_one
AssertionError: social-preview-howto.md states the split 28 REST + 6 MCP + 15 CLI without stating 49 next to it
```

即 `docs/reports/social-preview-howto.md` 写了「28 REST + 6 MCP + 15 CLI」的拆分，
却没有在同一处写出合计的 **49**；契约要求凡是说检查项数量的地方，都要把合计写在旁边。

第 3 次重打的红由**三条**断言造成（§3.4），除上面这条外，还有两条 `tests/test_doc_citations.py`：
引用漂移，以及 Release 正文引用的源指纹属于另一棵树。

### 4.4 一个容易读错的地方：专门叫「Public contracts」的 job 是**绿的**

两次红 run 里，`Public contracts (live)` 这个 job 都**成功**了。这不是矛盾：

- 该 job 跑的是 `scripts/verify-public-contracts.py`（[ci.yml:465](../../.github/workflows/ci.yml)），
  是一份**实测**脚本：起真的 uvicorn 服务、跑真的 demo APK，核对 API 到底响应什么；
- 让 `social-preview-howto.md` 变红的判据在 `tests/test_public_contracts.py` 里，
  是一个 **pytest** 用例，**只在套件（三个 test job）和重测量 job 里跑**。

所以「契约核对通过」和「文档里的契约说法与代码一致」是**两件事**，前者绿不代表后者绿。
**看 CI 结论时不能只盯着 job 名字像不像。**

### 4.5 `The report's figures describe the tagged tree` 只在 tag 上跑

这个 job 有 `if: startsWith(github.ref, 'refs/tags/')`（[ci.yml:496](../../.github/workflows/ci.yml)），
所以在 `main` 分支的 run 里它是 `skipped`（例如同一 commit 的 main run `44126948441`：
10 个 job 里 9 个跑、measurement 这一个 `skipped`）。

结论：**「这棵树自洽吗」只有 tag run 能回答**。main 分支全绿的 run，不能用来推断
`v1.0.0` 的 CI 结论；而恰恰是 tag 上的那个 measurement job，两次都红了。

### 4.6 「发布后修正并重打 tag」为什么必须有「等 CI 变绿」这一步

[发版清单 §3 步骤 8](v1.0.0-release-checklist.md) 写了这条路径，它的顺序里，
第 5 步是：

> **等新的 CI run 变绿**（旧 run 已作废：`gh run list --branch v1.0.0 --limit 1`
> 的最新一条 `headSha` 必须等于新 tag 指向的 commit，conclusion 必须是 success）

而它的四条判据里第 2 条是：

> tag 的 CI 最新一条 run 的 conclusion == success 且 headSha == 上述 commit

**这两次红说明的就是这条为什么不能省**：

1. 重打 tag 之后，**旧的绿 run 已经不能代表新 tag**——第 1 次和第 2 次重打的 run 都是绿的，
   但它们在第 3、4、5 次重打后全部作废；
2. 重打 tag **不等于**修好了。tag 指向一个 commit，**那个 commit 的 CI 结论是什么就是什么**，
   跟上一次 tag 的 CI 结论无关。第 4 次重打修掉了两条 `test_doc_citations.py` 断言，
   第 5 次重打修掉了 Release 正文的源指纹——但两次都还是红的，因为契约那条一直在红；
3. 因此判据只能是「**盯到最新那条 run 变绿**」，而不是「我推了 tag，我改了文档」。
   清单 §3 步骤 8 里那句「『推完 tag 就去写文档』是 v1.0.0 最后一次 tag 变红的直接原因」
   说的正是这件事——**没有人盯 run**。

### 4.8 最后一处红：测量脚本读 pytest 汇总行的正则跨行匹配

第 10–13 次重打**只红一个 job**：`The report's figures describe the tagged tree`。
它日志里说的是：

```text
  the tree has 1695 tests; the run accounted for 1682
  the self-checks agree with the refreshed report (nothing ran) after 2 round(s)
  the status page's self-checks: passed=3
```

账目少的那 13 项**正好是报告的自检轮** —— 代码轮 1678 passed + 1 skipped，
状态页自检 3 passed，树的 1695 = 1679 + 13 + 3。

根因在 `scripts/refresh-report-figures.py` 的 `outcome_counts()`：它用
`=+\s*(.*?)\s*=+` 找 pytest 的汇总行。`\s` 匹配换行，于是匹配可以从一行中间的
`=` 起 —— `assert 1682 == 1695` 里那个 `==` —— 跨到下一行，把打开汇总行的那串
`=` 吃掉；最后一个匹配成了汇总行的**空尾巴**，一轮跑了 13 项（挂了 1 条）的自检
被读成 **0 项**。

**为什么只有 CI 上犯**：pytest 只有在**有测试失败**时才会打出 `assert N == M` 那行。
本地自检轮全过，没有那行，正则就不跨行；CI 上自检轮挂了 1 条，才有 —— 那行的
`==` 就是唯一的触发点。所以本地怎么测都测不出来。

修法：匹配不许跨行（`[^\S\n]*` 与 `[^\n]*?`），并取最后一个**非空**捕获（一行
光秃秃的 `=` 也会产生空捕获）。回归测试按规矩做了红→绿：旧实现下正是
`assert 0 == 12`。修好之后第 14 次重打绿了。

> 这条根因能查出来，靠的是一个临时诊断 job：它 checkout **tag 那棵树**、给测量脚本
> 的每个子进程装探针，把退出码与输出尾巴打出来。没有它，同一句话「那一轮量出了
> 0 项」只能靠猜。
