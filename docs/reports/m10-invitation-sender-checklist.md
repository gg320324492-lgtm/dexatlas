# M10 独立验收 —— 发起人发送前清单

> **本文件的性质：** 这是**你自己**在发出 M10 独立验收邀请之前要做的每一步。
> 它不是读者要做的事——读者要做的事写在[邀请函成稿](m10-invitation-final.md)
> 与[读者验收包](m10-reader-package.md)里，本文件不复述它们。
>
> **怎么用：** 逐条勾。带命令的条目请把命令**在你自己的机器上跑一遍**，再和
> 「查过是什么样子」下面写的实测结果对照。那里写的是本清单编写时、在本仓库
> 某一棵提交上真实跑出来的结果，**不是**对读者的承诺：你换一台机器、换一棵树，
> 结果可能不同，对不上就以你实测的为准。
>
> **本清单不替你执行任何动作。** 它不填邀请函、不打 tag、不推送、不发送、
> 不联网，也不代你回答读者。涉及改动仓库或远端的条目，命令写在条目里，
> 跑不跑、什么时候跑，由你决定。

## 二、组二：钉死验收 commit（最容易出错的一处）

读者侧的第一道核对是：**clone → `git checkout v1.0.0` → `git rev-parse HEAD`**，
结果必须与邀请函 §2 里那一串**逐字相同**，否则读者会停下联系你。所以函里要填的
必须是**提交**的 hash，不是 tag 自己的 hash。

- [ ] **取提交 hash：用 `git rev-parse v1.0.0^{commit}`，不要用 `git rev-parse v1.0.0`**

  `v1.0.0` 是一个**带说明的 tag**（annotated tag）。`git rev-parse v1.0.0`
  返回的是**这个 tag 对象**的 hash；带 `^{commit}` 才是它指向的**提交**。

  查过是什么样子（本清单编写时）：

  ```text
  $ git rev-parse v1.0.0
  e937ca12c688b12be3de71195c412f844e6d50bd      ← tag 对象，不是它
  $ git rev-parse v1.0.0^{commit}
  8f9ddcaf7804841d77270c1fdb548110faecc598      ← 这才是要填进函里的
  ```

  填错的后果：读者 `git rev-parse HEAD` 拿到的永远是**提交**的 hash，
  与 tag 对象的 hash 永不相等——邀请在第一步就卡住，而卡住的原因看起来
  像「读者的 clone 出了问题」。

- [ ] **确认这个提交已经在 origin 上**

  ```bash
  git ls-remote origin refs/tags/v1.0.0            # tag 对象
  git ls-remote origin 'refs/tags/v1.0.0^{}'       # 它指向的提交——要核的是这一行
  ```

  查过是什么样子：两行分别返回 `e937ca12…` 与 `8f9ddcaf…`，与上一条一致，
  说明 tag 和它的提交都已经在 origin 上，读者 clone 后拿得到。

- [ ] **确认这个提交含本轮全部材料修正**（否则读者读到的是旧稿）

  ```bash
  git diff --name-only "v1.0.0^{commit}"..HEAD -- src/ tests/   # 期望为空
  git log --oneline "v1.0.0^{commit}"..HEAD | wc -l             # 落后多少个提交
  ```

  查过是什么样子：`src/` 与 `tests/` **一行没改**（发布出去的代码和它的
  测量数字不受影响），但材料目录**落后 45 个提交**——tag 里那份邀请函还是
  旧稿（开头写「本稿钉定了验收 commit，不再保留『待钉定』表述」），
  当前稿是留占位符等发起人填的版本。读者 `git checkout v1.0.0` 拿到的是
  **旧的那一份**。

- [ ] **所以发之前你要做一个选择**——两个都行，但得是你做的决定。

- [ ] **选 A：把 `v1.0.0` 重打到材料定稿的那个提交上**，再取 `^{commit}` 填进函里。
  读者 `git checkout v1.0.0` 拿到的才是修正后的材料。

  ```bash
  git tag -f -a v1.0.0 <材料定稿的提交> -m "v1.0.0 — ..."
  git push origin v1.0.0 --force
  git rev-parse v1.0.0^{commit}      # 重新确认要填的那一串
  ```

  tag 已经在 origin 上，移动它是一个**公开可见**的改动。读者还没拿到材料，
  现在动代价最小——但这件事本身该由你决定，本清单不代劳。

- [ ] **选 B：不动 tag**，函里就填 `8f9ddcaf…`，同时把函 §2 里「含本轮全部
  材料修正的版本」这句改掉——因为它不成立。改法随你，但不能留着
  一句与事实相反的话让读者去核。

- [ ] **无论选哪个，填进函 §2 的都必须是 `git rev-parse v1.0.0^{commit}` 的输出**，
  并把整串 40 位一字不差地贴进去（读者是逐字比对的）。

## 三、组三：确认本机环境与三个后端

- [ ] **三个分析后端在项目自己的 `.scratch/` 下**，不在系统盘、不在全局 PATH。
  `jadx` 与 `apktool.jar` 在 `.scratch/backends/`；`androguard` 是 Python 包，
  来自 `analysis` 这组依赖（`uv sync --extra dev --extra analysis`），
  不在 `.scratch/` 里。

- [ ] **`source .scratch/env.sh` 之后，三个后端都 available**

  ```bash
  source .scratch/env.sh          # 必须在项目根目录 source，见下
  uv run --no-sync dexatlas backends
  ```

  查过是什么样子：

  ```text
             Analysis backends
  ┌────────────┬───────────┬─────────┐
  │ Backend    │    Status │ Version │
  ├────────────┼───────────┼─────────┤
  │ jadx       │ available │ 1.5.2   │
  │ apktool    │ available │ 2.11.1  │
  │ androguard │ available │ 4.1.4   │
  └────────────┴───────────┴─────────┘
  ```

- [ ] **知道 `.scratch/env.sh` 是你本机的文件，仓库里没有**（`.gitignore` 忽略
  整个 `.scratch/`）。它做三件事：把 `DEXATLAS_JADX_PATH` 与
  `DEXATLAS_APKTOOL_JAR` 指向 `.scratch/backends/` 下的实际文件；把后端的
  安装目录（`INSTALL_ROOT`）指到项目里；把 uv 的缓存与临时目录也留在项目内。

- [ ] **知道 `source .scratch/env.sh` 必须在项目根目录执行**：脚本里的路径是
  相对当前目录写的，从别处 source 会得到指错的路径。

- [ ] **知道不 source 的后果**：`scripts/install-backends.sh` 与
  `scripts/fetch-jadx.py` 的安装目录会落到系统临时目录，项目里找不到后端。
  分析仍然会完成，但报告里会写明哪些步骤没跑——那正是读者要看的降级场景，
  可你自己发出邀请前应该确认本机走的是**完整后端**那条路。

- [ ] **不要把 `env.sh` 或后端的绝对路径贴给读者。** 邀请函 §8.3 写明「作者
  可以澄清名词含义，但不替您补命令、改环境」；读者材料给的是公开的安装
  路线（`docs/install.md`）。你自己的机器路径属于你，不属于材料。

## 四、组四：发出前跑一遍自查

- [ ] **在你要发出的那棵树上跑自查脚本**

  ```bash
  uv run --no-sync python scripts/m10_selfcheck.py
  ```

  查过是什么样子（末行与退出码）：

  ```text
  自动化判定：通过 40，失败 0，需人工 40；已判定项通过率 100.0%
  需人工项不是失败：它们要一位读者在真实机器上按验收包执行并记录。
  ```

  退出码 `0`。脚本的用法与判定口径见[自查报告](m10-selfcheck.md)。

- [ ] **「需人工 40」不是失败。** 那 40 项正是读者要亲手做的那 40 项——
  脚本替不了。脚本只判仓库自己能回答的那 40 项。

- [ ] **只要「失败」不是 0，就先修再发。** 脚本的退出码在有失败项时是 `1`。

- [ ] **见过「失败 1」也不用慌，先看是哪一项。** 最常见的一项是 `G.vulture`：
  它判的是「死代码检查工具在不在 PATH 上」。在一棵**没装 `dev` 依赖**的
  检出上跑，vulture 没装，这项就判失败——本清单编写时第一遍跑出来的正是
  「通过 39，失败 1，需人工 40」，失败项就是它。修法是把依赖装齐：

  ```bash
  uv sync --extra dev --extra analysis
  uv run --no-sync python scripts/m10_selfcheck.py
  ```

  装齐之后重跑就是「通过 40，失败 0」。若失败项**不是**这一项，那就是
  真的有问题，按它给的证据改完再发。

- [ ] **知道这个脚本只读**：它不写报告、不改徽章、不改任何数字；退出码
  `0` = 无失败项、`1` = 至少一项失败。

- [ ] **顺带确认材料里引用的几个数还成立**——不用你手数，自查脚本已经逐条核过：

  | 数字 | 自查项 / 出处 |
  |---|---|
  | 40 项检查表 / 19 个阻断项 | `PACK.40-items`、`PACK.19-blocking` |
  | 退出码 0–6 | `F1.exit-codes` |
  | MCP 工具 11 个 | `F3.mcp-tools` |
  | 公共契约活检 49 项 = 28 REST + 6 MCP + 15 CLI | `docs/architecture/public-contracts.md` |
  | 1,588 个测试（1,441 快 + 147 集成）、覆盖率 93.3% | `FIG.suite-adds-up`、`FIG.badge-tests`、`FIG.badge-coverage` |

- [ ] **不要手改任何数字。** 材料里的数字由脚本核对；发现自己想改的时候，
  改的是代码或文档，然后重跑脚本。

- [ ] **任何真实凭据**。发出前对要发出去的正文与附件扫一遍：

  ```bash

  ```

  查过是什么样子：命中两处，都是第一方 demo 样例**源码里的占位常量**
  （`tests/test_search_substring_fallback.py` 与
  `docs/case-studies/demo-app-walkthrough.md`）——随样例源码刻意提交的，
  不是真凭据。除此之外没有命中。你要确认的是：**除这两处已知占位符之外，
  没有真实凭据**；而邀请函、附件、你写的邮件正文里，一个 key 形状的字符串
  都不该出现。

- [ ] **知道仓库是公开的**：origin 指向 GitHub 上的公开仓库，读者 clone 就会
  看到仓库里的全部内容，包括上面那些草稿文件。所以「不要一起发出去」的
  准确含义是：**不作为附件、不摘录进邀请函或邮件**。如果连「读者 clone 后
  能看到 `docs/outreach/` 的草稿」这一点你也要挡，那属于发版决定，得在
  读者 clone 之前处理——本清单不替你做这个决定。

## 八、组八：发出之后留什么档

- [ ] **记下这一轮邀请的五样东西**：

  | 项 | 填什么 |
  |---|---|
  | 验收 commit | `git rev-parse v1.0.0^{commit}` 的整串 40 位 |
  | 发出时间 | 日期 + 时间（到分钟，够用来对日志） |
  | 收件人 | 姓名或代号 |
  | 约定反馈时限 | 与组一、组六一致 |
  | 实际发出的附件清单 | 逐项列出，含三个证据包与三篇正文 |

  再加一份**发出那版邀请函的副本**（含你填进去的 hash 与时限）。

- [ ] **放在只有你看得到的地方**：私人笔记或本地文件。对方的姓名、邮箱不要写进
  公开仓库——那是别人的联系方式。

- [ ] **对方交回结果时，先核一件事**：记录里 §1 的「commit hash」栏与档里那一串
  是否**逐字相同**。不相同，说明对方验的不是这一个提交，先问清楚再谈结论。

- [ ] **在读者交回之前，仓库里关于 M10 的状态一个字都别改。** 各份材料开头与
  `docs/status.md` 现在写的都是「独立验收尚未开始；M10 未完成」——这在
  读者交回之前是真话。
