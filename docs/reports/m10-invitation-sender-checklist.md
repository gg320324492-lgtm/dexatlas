# M10 独立验收 —— 发起人发送前清单（可执行版）

> **本文件的性质：** 这是**你自己**在发出 M10 独立验收邀请之前要做的每一步。
> 它不是读者要做的事——读者要做的事写在[邀请函成稿](m10-invitation-final.md)
> 与[读者验收包](m10-reader-package.md)里，本文件不复述它们。
>
> **怎么用：** 逐条勾。每一条都按同一个四段写：**查什么 → 怎么查（命令）→
> 查过是什么样 → 不通过怎么办**。带命令的条目请把命令**在你自己的机器上、
> 在你要发出的那一棵树上跑一遍**，再和「查过是什么样」对照。那里写的是本清单
> 编写时、在本仓库某一棵提交上真实跑出来的结果，**不是**对读者的承诺：你换一台
> 机器、换一棵树，结果可能不同，对不上就以你实测的为准。
>
> **本清单不替你执行任何动作。** 它不填邀请函、不打 tag、不推送、不发送、
> 不联网，也不代你回答读者。涉及改动仓库或远端的条目，命令写在条目里，
> 跑不跑、什么时候跑，由你决定。
>
> **本清单不替你做验收。** 全清单跑完，你手里的仍然是一份「准备完毕」的邀请，
> 不是一份验收结论；M10 的判定只来自读者。

## 0. 三分钟版

时间紧的话先跑这四条，其余的回头补：

```bash
git rev-parse "v1.0.0^{commit}"        # 组二：验收 commit（注意 ^{commit}）
source .scratch/env.sh && uv run --no-sync dexatlas backends   # 组四：三个后端
uv run --no-sync python scripts/m10_selfcheck.py                # 组五：自查，期望退出码 0
git status --porcelain                  # 组七：工作区必须干净
```

## 二、组二：钉死验收 commit（N1；全流程最容易出错的一组）

> **这一组的教训（第三轮读者走查 N1）：** 「重打 tag 之前不能发邀请函」。
> 材料改完而 tag 没跟上，读者 `git checkout v1.0.0` 拿到的是**另一棵树**，
> 会做出一份针对另一棵树的验收结论。发信前必须把「发出去的那棵树」钉死，
> 并让函里的 hash、tag 指向、记录模板三者指向**同一个**提交。

- [x] **查什么：** 取提交 hash——必须用 `git rev-parse v1.0.0^{commit}`，
  **不要**用 `git rev-parse v1.0.0`。

  **怎么查：**

  ```bash
  git rev-parse v1.0.0                  # tag 对象自己
  git rev-parse "v1.0.0^{commit}"       # 它指向的提交——要填进函里的
  git cat-file -t v1.0.0                # 应为 tag（附注 tag）
  ```

  **查过是什么样：** 命令的**形状**如下——**下面的 hash 是示意，必须现查现填**：
  tag 每重打一次就换一次串，写死在这里的串发出时一定是错的。

  ```text
  $ git rev-parse v1.0.0
  <40 位 tag 对象 hash>              ← tag 对象，不是它
  $ git rev-parse "v1.0.0^{commit}"
  <40 位提交 hash>                  ← 这才是要填进函里的
  $ git cat-file -t v1.0.0
  tag
  ```

  自查的判据是**形状不是数值**：`git cat-file -t v1.0.0` 打印 `tag`，且两条
  `rev-parse` 的输出**互不相同**（附注 tag 时必然如此——这一点在第三轮走查里
  被写成过一次「卡死第 1 步」的缺陷）。

  **不通过怎么办：** 先看 `git cat-file -t v1.0.0`：若不是 `tag`，说明这是轻量
  tag，两条命令本来就相等，按上面第一行填即可。填错的代价是：读者
  `git rev-parse HEAD` 拿到的永远是**提交**的 hash，与 tag 对象的 hash
  永不相等——邀请在第一步就卡住，而卡住的原因看起来像「读者的 clone 出了问题」。

- [x] **查什么：** 这个提交**已经在 origin 上**，且 tag 也推过去了。

  **怎么查：**

  ```bash
  git ls-remote origin refs/tags/v1.0.0            # tag 对象
  git ls-remote origin 'refs/tags/v1.0.0^{}'       # 它指向的提交——要核的是这一行
  ```

  **查过是什么样：** 两行应当**分别**对应上一条的「tag 对象」与「提交」——
  `refs/tags/v1.0.0` 那行是 tag 对象，`refs/tags/v1.0.0^{}` 那行是它指向的提交，
  **要核的是第二行**，且它必须与函里填的那一串逐字相同。
  （本清单编写环境不联网，这一组**未实测**，请你自己跑。）

  **不通过怎么办：** `git push origin v1.0.0` 再核一遍。读者 clone 后拿不到
  这个 hash，函里的一切都作废。

- [x] **查什么：** tag 指向的那棵树**含本轮全部材料修正**（读者读到的是定稿，
  不是旧稿）。

  **怎么查：**

  ```bash
  git diff --name-only "v1.0.0^{commit}"..HEAD -- docs/reports/m10-*.md  # 只应有填 hash 这一步动过的文件
  git diff --name-only "v1.0.0^{commit}"..HEAD -- src/ tests/            # 期望为空
  git log --oneline "v1.0.0^{commit}"..HEAD | wc -l                     # tag 落后几个提交
  ```

  **查过是什么样：** 第一条**只应列出「填 hash 这一步」动过的文件**——邀请函 §2、
  验收记录模板 §1 的 commit hash 栏，以及随之改判据的发送清单与准备清单；M10 材料
  在 tag 指向的树里与你手上的其余部分仍是同一份，读者读到的是定稿。第二条**必须为空**：
  材料修正不该动 `src/` 与 `tests/`，发出去的代码和它的测量数字不受影响。
  第三条告诉你 tag 落后几个提交（填完 hash 后是 1）。

  **为什么第一处差异是应有的**：填 hash 那一步之后 tag **不再重打**
  （下一条 N2：「填完不要再改 tag」）。**一份点着 tag 自己的提交的文件不可能在 tag
  里面** —— 它要写的就是 tag 指向的那一串 hash。这不是「读者读到旧稿」：读者 clone
  之后 `git checkout v1.0.0` 拿到的提交，与函里那一串**逐字相同**（这一条由
  「以读者的身份复核」那一项验过）。

  **不通过怎么办：** 除填 hash 那两行之外还有材料改动 = **N1 未关闭**，此时**不能
  发信**。往下走「重打 tag」那一条——但**填完 hash 之后就不能再重打**了。

- [x] **查什么：**（N1 的动作）把 `v1.0.0` **重打**到材料定稿的提交上。

  **怎么查：**

  ```bash
  git tag -f -a v1.0.0 <材料定稿的提交> -m "v1.0.0 — 材料定稿"
  git push origin v1.0.0 --force
  git rev-parse "v1.0.0^{commit}"      # 重新取要填的那一串
  ```

  **查过是什么样：** 重打后上面第一条命令会打印出新的那一串；它必须与
  `git log --oneline -1 <材料定稿的提交>` 指向同一个提交。

  **不通过怎么办：** tag 已经在 origin 上，移动它是一个**公开可见**的改动。
  读者还没拿到材料，现在动代价最小——但这件事本身该由你决定，本清单不代劳。
  如果你**决定不动 tag**，那函 §2 里「含本轮全部材料修正的版本」这句就不成立，
  必须改掉；不能留一句与事实相反的话让读者去核。

- [x] **查什么：**（N1 的动作）把**同一串 40 位 hash** 写进邀请函 §2 与
  验收记录模板。

  **怎么查：**

  ```bash
  grep -n "commit 【待填" docs/reports/m10-invitation-final.md   # 应无命中
  grep -n "commit hash" docs/reports/m10-review-record-template.md
  ```

  **查过是什么样：** 本清单编写时，邀请函 §2 仍是
  `commit 【待填：v1.0.0 发版 commit 的完整 hash】`（**这一处是故意留的**，
  因为 tag 会被重打，那一串必须现查现填）；记录模板 §1 的「commit hash」一栏
  已注明「照抄邀请函成稿 §2 钉定的那一串完整 hash」。

  **不通过怎么办：** 填完再跑一次上面的 `grep`：还有 `【待填` 命中就说明没填。
  填的时候整串 40 位一字不差地贴（读者是逐字比对的），并且**填完不要再改
  tag**——改了 hash 就对不上了。

- [x] **查什么：** 以**读者的身份**复核第 1 步（这是最省事的发信前自检）。

  **怎么查：**

  ```bash
  git clone <repo> .scratch/reader-check && cd .scratch/reader-check
  git checkout v1.0.0 && git rev-parse HEAD
  ```

  **查过是什么样：** 输出的 40 位 hash 与邀请函 §2 里那一串**逐字相同**。

  **不通过怎么办：** 不一致就不要发信——读者会在第一步就停下并联系你，
  而那时你要么找不到原因，要么已经晚了。

## 五、组五：发出前跑一遍自查

- [ ] **查什么：** 在**你要发出的那棵树**上跑自查脚本，退出码必须是 0。

  **怎么查：**

  ```bash
  uv run --no-sync python scripts/m10_selfcheck.py
  ```

  **查过是什么样：** 两个环境两个结果，**不是矛盾**：

  | 环境 | 输出 | 退出码 |
  |---|---|---|
  | 装齐 `dev` extras（仓库落盘快照，`docs/reports/m10-selfcheck.md`） | `通过 43，失败 0，需人工 40；已判定项通过率 100.0%` | 0 |
  | 没装 `dev` extras（本清单编写时的机器） | `通过 42，失败 1，需人工 40`（唯一失败项 `G.vulture`） | 1 |

  **不通过怎么办：** 若失败项是 `G.vulture`（判的是 vulture 在不在 PATH/venv 里），
  装齐依赖重跑：

  ```bash
  uv sync --extra dev --extra analysis
  uv run --no-sync python scripts/m10_selfcheck.py
  ```

  装齐之后重跑就是「通过 43，失败 0」。若失败项**不是**这一项，那就是真的
  有问题，按它给的证据改完再发。

- [ ] **查什么：** **「需人工 40」不是失败**；它和「43 条自动化判定」不是
