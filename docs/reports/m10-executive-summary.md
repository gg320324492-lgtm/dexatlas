# M10 独立验收 · 读者执行摘要

> 一页看懂：你被邀请做什么、怎么做、要多久、交回什么。
> 细节见[读者验收包](m10-reader-package.md)与[验收邀请函成稿](m10-invitation-final.md)。

## 这个项目是什么

**DexAtlas 是一个开源、证据优先的 Android 静态分析工具**：给它一个 APK，
它用三个分析后端（Apktool、JADX、Androguard）解析清单与代码，把结果存入
SQLite 工作区，渲染出 Markdown / JSON 报告与证据包——报告里的每个结论都
要能通过引用回溯到它读过的那几行代码。

## 验收要回答什么问题

> **一个没参与开发的人，能不能只靠仓库文档，把 DexAtlas 装起来、
> 跑通一个完整分析案例，并核对报告结论确实能追溯到代码？**

这不是问答打分：你需要对 **40 项检查表**逐项给出
「通过 / 不通过 / 未验证」三态判定。其中 **19 项是阻断项（标 ★）**，
任何一项不通过，整个验收即不通过。检查表见
[验收准备包 §2](m10-acceptance-pack.md)。

## 你要做的 5 步

1. **锁定验收对象**：验收对象是 `v1.0.0` 这个 tag 所指的提交——你执行
   `git checkout v1.0.0` 就能拿到它，**不必再向发起人索取 commit hash**；
   想核对时用 `git rev-parse v1.0.0` 核出 hash，与
   [邀请函成稿 §2](m10-invitation-final.md) 占位符里填的那串逐字比对。
   全程只验这一个提交，**不要用移动的 `main` 分支**。
2. **clone 并装环境**：`git clone` → `git checkout v1.0.0` →
   `uv sync --extra dev --extra analysis --extra mcp --extra demo`
   （或走 Docker 路线）。命令见[读者验收包 §3.1–3.2](m10-reader-package.md)。
3. **跑一个完整案例**：对 `demo.apk` 做分析，做检索与引用核对，
   导出三格式报告与证据包（[读者验收包 §3.3–3.7](m10-reader-package.md)）。
4. **逐项判定并打分**：对照 40 项检查表给三态判定，再按
   [准备包 §5](m10-acceptance-pack.md) 的空白表对 GitHub / Upwork
   两套权重打分，每项附扣分理由。
5. **交回记录**：把过程填入
   [验收记录模板](m10-review-record-template.md)，
   按[提交格式](m10-reader-package.md)交回发起人。

## 预计耗时

- 到第一份报告：首次约 **10–20 分钟**（含下载），暖缓存约 **1.5–2 分钟**
  （同一环境差异下 [M8 演练](m8-install-rehearsal.md)另测过约 30 秒，
  以你自己的实测为准；口径说明见[读者验收包 §5.4](m10-reader-package.md)）。
- 完整案例（analyze 到 xrefs）：约 1–2 分钟。
- 40 项判定 + 两平台打分：视抽查深度，**整体建议预留半天**。

## 你会产出什么

**一份填写完成的[验收记录模板](m10-review-record-template.md)**（Markdown），
含记录元数据、A/B/D 组逐项会话记录、卡点记录、客户视角审阅备忘
（三问结论、3 条引用抽查、红旗清单）与 GitHub / Upwork 两张评分表。
原始日志与截图留在你自己的机器上，记录需脱敏，不要自行 push 到仓库。

## 哪些项是自动化的，哪些必须人工判定

- **可自动化预检**：40 项中的文档完整性、链接可解析性、契约清单一致性、
  徽章与报告数字一致性等检查，已由
  `uv run --no-sync python scripts/m10_selfcheck.py` 自动执行
  （详见[m10-selfcheck.md](m10-selfcheck.md)）。发起人已在验收前跑过；
  你也可以在自己检出的 commit 上重跑，退出码 0 表示无失败项。
  **它只帮你省时间，不替代你的任何判定。**
- **必须人工判定**：安装是否真的走通、案例结论是否与你的复现一致、
  引用能否真的定位到代码、事实与线索是否分得清、报告是否如实说明
  哪些后端没运行、评分表里的每一分——这些都要你**亲手执行并记录**。
  作者自述的任何数字，在你复现之前一律视为未验证。

## 两条铁律

1. **你的判定只依据你自己执行命令得到的输出**；作者可以澄清名词，
   不能替你补步骤。
2. **预期与实际不一致时，以实际为准**，把差异写成卡点——文档缺步骤
   本身就是缺陷，不要替项目圆场。
