### 一、我们邀请您做什么

DexAtlas 已完成从安装到交付样例的开发，现邀请你对已发布的 v1.0.0（tag 2026-11-17）做独立验收：
**独立验收**。我们想请您以一位从未参与开发的真实读者的身份，回答一个问题：

> **一个不认识我们的人，能不能只靠仓库里的文档，把 DexAtlas 装起来、
> 跑通一个完整分析案例，并核对报告里的结论确实能追溯到代码？**

具体包括三部分：

1. **首次读者路线**：从 `git clone` 开始，完成推荐安装路线，对一个演示 APK
   做一次完整分析，导出报告与证据包（验收项 A、B、D 组）。
2. **客户视角审阅**：不安装也能做的部分——阅读三个交付案例，判断
   「输入与结论是否清楚」「引用能否核查」「事实与线索能否区分」（C、D 组）。
3. **评分**：按既有的六维度、双平台权重（GitHub / Upwork）重新打分，
   每项附扣分理由（模板见[验收准备包 §5](m10-acceptance-pack.md)）。

完整的 **40 项检查表**（含 19 项一票否决的阻断项）见
[验收准备包](m10-acceptance-pack.md)。**您只需要逐项给出
「通过 / 不通过 / 未验证」三态判定之一，没有「大概可以」。**

### 二、您需要准备什么

| 项目 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows 11 或 Linux | 两者有实测记录；macOS 未验证，如使用请如实记录 |
| Python | 3.12 或 3.13 | 项目 CI 在两个版本上运行 |
| [uv](https://docs.astral.sh/uv/) | 最新版 | Python 包与环境管理器；安装方式见[其官方文档](https://docs.astral.sh/uv/getting-started/installation/) |
| JDK | 21+（可选） | 仅 JADX / Apktool 后端需要；没有 Java 也能用 Androguard 完成基础分析 |
| Docker | 可选 | 不想装 Python/JDK 时走 Docker 隔离路线 |
| 网络 | 首次需要 | clone、依赖与后端下载；装好后分析本身可离线 |
| 磁盘 | 预留数 GB | 依赖、后端与分析产物；不要写到系统盘根目录 |

JADX 与 Apktool 是可选的第三方后端，不是本仓库依赖：没有它们，分析仍然
完成，只是报告中会写明哪些步骤未运行（这本身就是一项验收内容）。获取方式
写在 [docs/install.md](../install.md)。

### 三、执行步骤（约半天）

1. **领取固定 commit**：本次验收针对**验收发起人指定的一个固定 commit**
   （本轮已钉定为 `277d0fa`，见文首说明；后续轮次由发起人在发出的副本中
   重新钉定并告知 hash；发出邀请时该 commit 应已推送）。全程只验这一个
   提交；不要用移动的 `main` 分支。
2. **clone 并检出**：按[读者验收包 §3.1](m10-reader-package.md) 执行
   `git clone` 与 `git checkout <commit>`。
3. **环境准备**：按[读者验收包 §3.2](m10-reader-package.md) 执行
   `uv sync --extra dev --extra analysis --extra mcp --extra demo`
   （或 Docker 路线），运行 `uv run dexatlas backends` 确认后端状态。
   环境前提摘要：Windows 11 或 Linux；Python 3.12/3.13；最新版
   [uv](https://docs.astral.sh/uv/)；JDK 21+ 与 JADX/Apktool 可选（缺失时
   分析仍完成并如实记录降级）；首次需要网络下载依赖与后端；预留数 GB 磁盘。
4. **逐项执行**：按[读者验收包 §3](m10-reader-package.md) 的分步路径完成
   首次分析、案例核对与证据核查。每步记录命令原文、退出码、关键输出与耗时。
5. **逐项判定与打分**：对照[准备包 §2 的 40 项检查表](m10-acceptance-pack.md)
   逐项给出三态判定，再按[准备包 §5](m10-acceptance-pack.md) 的空白表给
   GitHub / Upwork 两套权重打分。
6. **填写并交回记录**：把上述过程填入
   [验收记录模板](m10-review-record-template.md)，按
   [读者验收包 §5.3 的提交格式](m10-reader-package.md)交回发起人。

**时间预估**：从 clone 到第一份报告，冷缓存（含依赖与后端下载）约 10–20 分钟，
暖缓存（JDK/uv 已就绪）约 1.5–2 分钟；完整案例（analyze 到 xrefs）约 1–2 分钟；
Docker 路线另加约 2 分钟镜像构建；40 项判定加两平台打分视抽查深度而定，
**建议整体预留半天**。

### 四、您的判定如何被使用

- 您填写的记录是 **M10 里程碑能否关闭的唯一依据**：19 个标 ★ 的阻断项中
  任何一个「不通过」，M10 即不通过；后续修复后需要复验的也只是受影响项。
- 记录中发现的缺陷会转化为修复任务；修复完成后再请您复验受影响项。
- 您的评分将作为 v1.0.0 发版说明与作品集材料的输入；无论分数高低，
  都会原样引用，不会删改。
- 如果您同意，我们会在发布材料中致谢您（可用代号）；不同意则完全匿名。

### 五、独立性要求

为使结论可信，请您遵守：

1. **未参与实现**：您没有为本项目写过代码、文档或做过评审。如曾参与，
   请如实告知，发起人会另行安排。
2. **不采信作者自述**：README、案例、报告中的每个数字，要么由您重跑命令
   复现，要么记「未验证」。作者的解释只能作为线索，不能作为证据。
3. **作者不补步骤**：发起人可以澄清名词含义，但不替您补命令、改环境或
   远程操作您的机器。凡是靠发起人口头补充才走通的步骤，相关验收项判不通过。
4. **固定 commit**：全程只验发起人指定的那一个提交，所有记录写明 hash。
5. **如实记录**：预期输出与实际输出不一致时，以实际输出为准，把差异写成
   卡点；文档缺步骤本身就是缺陷，不要替项目圆场。

### 六、结果反馈方式

- **提交物**：一份填写完成的[验收记录模板](m10-review-record-template.md)
  （Markdown 文件），含记录元数据、逐项会话记录、卡点记录、客户视角备忘、
  源码评审记录（如您承担该角色）与两平台评分表。
- **提交渠道**：`［邮箱 / issue 链接 / 其他渠道——由发起人在发出的副本中填写］`。
- **原始日志与截图**：留在您自己的机器上，**不要上传**；记录中涉及的
  个人路径、密钥等敏感信息请用 `<redacted>` 脱敏。
- **不要自行 push 到仓库**；如发起人要求归档，按其指定渠道提交。
- **反馈时限**：建议自收到本邀请起
  `［N 个工作日 / 两周——由发起人在发出的副本中填写］`内完成；如需延长请
  随时告知。
