# Portfolio Freeze 声明

> **性质：** M15 步骤 7 的 Portfolio Freeze 声明草稿，与[执行单 §8](../roadmap/phase4-plan.md) 的冻结规则一致。
> **生效时机：** 本页是草稿，不代表项目已经冻结。正式冻结自 **Phase 4 源码评审通过并标记为完成之日**起生效（评审记录：[phase4-release-review.md](../reports/phase4-release-review.md)；状态收口随该评审落地）。

## 冻结什么

自 Phase 4 收口之日起，项目默认进入 Portfolio Freeze：**没有真实用户信号时，不启动下一阶段的功能开发**，也不新增后端、分析规则、页面、平台或展示性功能。

这不是停止维护，而是把范围锁定在已经验证过的交付物上——不因「看起来还能加」而扩张，只因「有真实信号」而重开。

## 什么信号才能解冻

重新规划新开发阶段的**唯一依据**，是出现以下真实信号之一：

1. **真实用户**按公开文档完成安装，并留下可复核反馈；
2. **真实客户**提出与证据链能力直接相关的需求；
3. **外部贡献者**提交 issue、PR 或复现报告；
4. **实际使用记录**表明核心流程存在阻塞问题。

宣传曝光、点赞、浏览量、stars 一类**不是**解冻信号；信号必须可复核、与项目本身的使用相关。

## 冻结期允许的四类维护

冻结期**允许且只允许**以下四类维护：

1. **安装与发布阻塞** —— 影响安装、启动、发布或核心路径可用的问题；
2. **安全问题** —— 依赖漏洞、数据处理或对外暴露的安全缺陷；
3. **依赖兼容性** —— 上游 breaking change、Python / Node 版本兼容等；
4. **文档事实错误与链接错误** —— 与外部实际状态不符的陈述、失效引用、错误数字。

## 冻结期维护的纪律

- 每类维护仍需**回归测试、可复核记录或明确的手工验证**——「顺手修了」不算完成；
- 报告与徽章的**数字由测量脚本生成**（`scripts/refresh-report-figures.py`），不手写；
- 状态文案（status / 路线图 / README / HANDOVER）随实际状态**同步更新**；
- 公共契约（API、MCP、CLI、报告、退出码）继续遵循「兼容变更显式记录、破坏性变更显式版本化」的既有规则（[公共契约 §6](../architecture/public-contracts.md)）；
- 新后端、新分析规则、新页面、新平台和展示性功能，必须等到**新的范围评审**完成后再决定。
