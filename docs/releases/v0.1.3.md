# DexAtlas v0.1.3 — Evidence That Points Back

**A conclusion you cannot point back to is not a conclusion.** v0.1.3 is the release
that makes that claim true of more things than it used to be: cross-references become
evidence, a loc travels with the report, a string constant knows where it is used, and
the documentation is checked against the code it describes.

---

## What changed

This release is about one idea, applied in seven places.

### Cross-references are evidence now

A cross-reference used to be something you could look up and nothing more. `dexatlas
xrefs` found the callers, but no conclusion in a report was ever built on one — the
method that recorded them was never called.

Now the pipeline records one `cross_reference` record per **called method** of the
analysed APK: "this method is called from N locations", with the call sites
attached. The unit is the callee rather than the call, and calls into library code
stay in the index without becoming a claim about the application under analysis —
`java.lang.StringBuilder.append` is a fact about the JDK.

### Every locator travels

A locator used to be a pointer that only worked on the machine that produced it.
JADX's was an absolute path:

```
jadx 1.5.2 -> jadx:G:/dexatlas/build/.../sources/com/example/demo/Crypto.java
```

A report carried a pointer to a filesystem, and to nothing else. Worse, the two halves
of a single record were not even the same kind of thing: Androguard's locator named a
place inside the APK, JADX's named a place on a disk.

Locators now have one shape — `<tool>:<place>` — where the place is relative to the
artefact the tool names: the APK for Androguard, the output tree for JADX and
Apktool. A workspace indexed by an earlier version still reads back in the current
form, so no migration is needed.

### A string constant knows where it was used

`StringConstant` had fields for the class and the method it came from, and nothing
ever filled them. A hardcoded key could be found in the index; it could not be traced
to the code that uses it.

The bytecode walk that collects cross-references now records the use sites as well,
at no extra cost — a constant used in two methods is two rows, one per place. Pool
entries that no instruction loads — type descriptors, member names — still carry no
location, because nothing loads them. **In the pool is not the same as used in code.**

### A method id has one spelling

The methods table and the cross-reference table stored the same method differently, so
an id copied out of `dexatlas methods` never resolved in `dexatlas xrefs` — for any
method with two or more arguments. There is one spelling now, in the model, in the
store and in the lookup.

### The counts match the tables

Analysing the multi-dex sample printed 14 methods where the table held 11 rows: the
same class defined in two dexes was collapsed by the store but counted twice by the
pipeline. The counts come from the tables now, and the definitions that collapsed into
one row keep both provenances, so the fact that they were in two dexes is still there.

### The flags say what they mean

`decompiled` was set from "this method has a code item in the DEX", which is not
"JADX decompiled this method" — and it was true of nearly every method in every APK.
It says what it says now: JADX is the only backend that can answer the question, so
the pipeline reads JADX's own output.

A `JADX WARN` comment above a method is no longer counted as a failure, and a
constructor is recognised by having no return type rather than by its name — a
constructor called `<init>` and an obfuscated method called `init` are different
things.

The cross-reference `kind` had the same problem: its documentation listed five ways
a call can be made, and the code only ever produced one. It is read from the bytecode
instruction now, so a static call and a virtual call are distinguishable.

### The documentation is checked against the code

The report and the provenance document cite specific lines of specific files. Nothing
checked that those citations still said what they claimed. Now
`scripts/check-doc-citations.py` reads every citation and verifies that the symbol
the sentence names really is in the cited range — 82 of them.

Nine places where the documentation said one thing and the code did another were found
this way, plus three smaller ones. The merge rule for a class's `kind` was written
backwards; the coverage table listed two modules above the threshold it claimed to be
limited to; a code block was attributed to the wrong test.

## What else was wrong

- **An empty backend path did not disable that backend.** The documented three-state
  semantics — unset means "look on `PATH`", empty means "do not use this one", a path
  means "use this" — were only two states, because an empty string was skipped and the
  lookup fell through to `PATH`. The strict `xfail` that recorded the defect is now a
  plain assertion test.

  The old tests around it passed for the wrong reason: they cleared `PATH` *and* set
  the empty string, so "returns nothing" was true either way. Fixing it or not made no
  difference to them.

- **The `LIKE` prefix filter did not escape the underscore.** `--prefix
  com.example.com_ex` also matched `com.example.comXex.Gamma`, because `_` is a
  wildcard in SQL and underscores are legal in Android package names. The answer was
  wrong, not merely fuzzy.

- **The exported-component evidence carried no tool version.** One report held
  `apktool 2.11.1 -> AndroidManifest.xml` next to `apktool ->
  AndroidManifest.xml#/application`: the same tool, the same run, one record with a
  version and one without. The versions are probed before the evidence is built, so a
  record cannot be written without them; `None` now means exactly one thing — the tool
  did not run.

- **The CLI saw less than the API it fronts.** `dexatlas classes` printed the first
  two sources of a class and said nothing. It still folds, but it now says how much it
  left out and how to see the rest.

- **The version was wrong in two places at once.** The published packages called
  themselves 0.1.0 after v0.1.1 and v0.1.2 had shipped. The version lives in one
  place now and the build reads it from there.

## Verification

| Configuration | Result |
|---------------|--------|
| All backends installed | 444 passed |
| Apktool only, JADX absent | 444 passed |
| No backends installed | 394 passed, 50 skipped |

First-party coverage is **93.9%**. `mypy` strict and `ruff` lint and format are clean.

CI now runs **six** jobs: Python 3.12, Python 3.13, a configuration with one backend
deliberately absent, a Docker build, a dependency audit, and a lint job that includes
`actionlint` over the workflow files themselves.

That last one is there because of how this release went. Two pushes produced a run
that failed without scheduling a single job — no message, nothing to retry — and it
looked like a platform fault. The cause was one line: a job-level `env:` block using
`${{ runner.temp }}`, which GitHub does not allow there. A YAML parser cannot see
that, which is why it took three steps to find.

## Known limitations

- **The samples are small** — the largest is under 3 KB. The *layouts* are covered;
  the *scale* is not. There is still no large-APK data point, so index performance and
  the instruction limits have never been under real load.
- **The obfuscated sample is hand-written** obfuscation, not a realistically hardened
  APK with control-flow obfuscation.
- **A Smali fallback carries no provenance.** When `class_source` returns Smali
  rather than Java, the caller cannot tell from the return value which backend
  produced it, and has to infer it from the shape of the workspace.

The full list, with the decisions behind it, is in
[the execution report](https://github.com/gg320324492-lgtm/dexatlas/blob/main/docs/reports/phase1-execution-report.md).

## Upgrade

```bash
git pull
uv sync --extra dev --extra analysis
uv run pytest
```

Nothing in the public interface changed. This release changes what the tool
*records* and what it *says*, and makes the documentation checkable.
