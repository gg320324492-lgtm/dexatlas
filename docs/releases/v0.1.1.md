# DexAtlas v0.1.1 — Foundation Hardening

**A fallback that never fired.** v0.1.1 is a bug-fix release: the Smali fallback — the
thing that keeps a finding verifiable when decompilation fails — had never worked. Not
for multi-dex APKs, not for single-dex APKs, not for any APK. This release fixes it and
explains why a defect like that can hide behind a green build.

---

## What changed

One fix, with two smaller defects found alongside it.

### The Smali fallback now works

When JADX cannot reconstruct a method, the bytecode is still there. DexAtlas falls back
to Apktool's Smali so the method can still be shown and verified. That fallback had
never run.

`smali_path()` searched for the per-dex directories **inside** `smali/`:

```python
smali_root = output_dir / "smali"              # the root
for root in sorted(smali_root.glob("smali*")):  # looking inside it
```

But Apktool writes `classes2.dex` to `smali_classes2/`, a **sibling** of `smali/`, not
a child of it — so the glob never found it.

Single-dex APKs failed too, and that is the part worth dwelling on. The class-name
conversion was correct all along; the *search scope* was wrong from the start. The glob
only ever matched subdirectories of `smali/` whose name began with "smali", and a
normally decoded APK has none — so the loop body never executed and the function
returned `None` for every class.

The directories are now discovered as siblings under the output directory and searched
in sorted order, so a class name present in two dexes resolves to the same file on
every call.

### A hostile class name could crash the analysis

The class name was joined into a path without validation. A name like
`....//....//etc/passwd` reached `Path.with_suffix()` and raised `ValueError` — an
unhandled exception, in an architecture where backend failure is deliberately a value
rather than a crash. A name that is not a class name now returns `None`.

### Dead code removed

`_is_single_component()` tested for empty and dot-only segments that its only caller
had already rejected — unreachable code, which is worse than no code because it looks
like a guard. It is removed, and a test now pins the caller's contract so the
traversal protection cannot quietly lapse.

## Why this one is worth a release note

The failure did not look like a failure.

Analysis completed. The report rendered. No error was recorded. `dexatlas source`
simply reported "No source" — which is exactly what an APK with no readable code
looks like.

That is the failure mode this project exists to prevent: **a result that cannot be
traced back to its cause.** An APK that defeats JADX entirely would have produced a
report with no code in it, and nothing in that report would have said why. The absence
was indistinguishable from the finding.

Two related failures were found while fixing this one, and both had the same shape:

- The integration test needed a fixture that `scripts/fetch-fixtures.sh` did not fetch.
  The test skipped on every machine that ran the script, CI included. **Both sides were
  green.** The guard was gone and nothing said so.
- The test then failed on CI and passed locally, because it made JADX disappear by
  pointing its configured path at a directory that does not exist — which does not
  disable a backend, since resolution falls back to a `PATH` lookup. A test that fails
  only on someone else's machine is worse than no test, because it makes you suspect
  the CI instead of the test.

A check now keeps the fixture list and the integration tests in agreement, in both
directions, and the fallback test no longer depends on what happens to be installed.

## Verification

The new tests fail **11 ways** on the unfixed code (6 integration, 5 unit) and pass
after. The integration tests analyse a real two-dex APK with JADX made unavailable,
because that is the only configuration in which the fallback is the thing under test.

| Configuration | Result |
|---------------|--------|
| All backends installed | 243 passed, 1 xfailed |
| Apktool only, JADX absent | 243 passed, 1 xfailed |
| No backends installed | 234 passed, 9 skipped |

First-party coverage is **89.1%** (1523/1709 lines), up from 87.8%. The Apktool
adapter, previously one of the weakest files at 82.7%, is now 94%.

`mypy` strict and `ruff` lint and format are clean. GitHub Actions is green on Python
3.12 and 3.13.

## Known issue

**An empty backend path does not disable that backend**, although `settings.py`
documents that it should — the path is skipped and a `PATH` lookup follows, so there is
no way to disable a backend through configuration. This predates v0.1.1 and is not
fixed here; it is recorded as a strict `xfail` test, which means the day it is fixed
the test fails and the marker has to be removed. Reported in
[the execution report](https://github.com/gg320324492-lgtm/dexatlas/blob/main/docs/reports/phase1-execution-report.md).
