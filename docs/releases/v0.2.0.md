# DexAtlas v0.2.0 — The Agent Layer, Open to a Caller

**A workspace an agent can ask, and an agent that has to prove what it says.**
v0.2.0 is Phase 2's first four milestones in one release: the analysis core made
safe for programmatic access (M0), a read-only MCP server over the workspace (M1),
a single evidence-first agent (M2), and a benchmark harness that measures all of
it (M3). The web workbench carries six of its eight screens. The benchmark view
and the screen-level work behind it are still being built, and this document says
so where it matters rather than counting them in.

---

## What changed

### The analysis core is safe for programmatic access (M0)

Phase 1's review found that the pipeline an agent would call was not the pipeline
the CLI had been exercising. Five contracts were rebuilt before anything was
exposed:

- **A method is resolved by descriptor, not by name.** `read_method_source` took
  the first declaration whose *name* matched, so a class with two overloads of
  `sign` answered every request with whichever one the decompiler happened to
  write first — and the body of the wrong overload reads exactly like the body of
  the right one, all the way into an agent's answer. A request may now carry a
  descriptor (`--descriptor` on the CLI, `?descriptor=` on the API), and an
  ambiguous name is reported as an ambiguity — exit code 4 on the CLI, `409` on
  the API — with the candidates and their descriptors in the error.
- **One analysis is one snapshot.** An `AnalysisRun` carries its own identity, and
  symbols and evidence are committed together, so a reader cannot see the symbols
  of one run beside the evidence of another.
- **A cross-reference row says where the call happened.** The index holds **call
  sites** now — each carrying the DEX file it was read out of and the instruction
  offset it sits at — and a **call edge** is derived from the sites rather than
  stored beside them. The report states the two numbers separately (`Call sites
  indexed` beside `Call edges indexed`), because two units side by side invite a
  ratio that was never there.
- **A verified observation has to prove its provenance.** `VERIFIED` was
  constrained by one rule that looked right; it now requires a validated
  provenance record, and a record that says the evidence was insufficient cannot
  be the ground a conclusion stands on.
- **One APK's analyses no longer share a workspace directory.** Every run writes
  into a directory of its own, so two analyses of the same APK cannot overwrite
  each other's intermediate files.

### A read-only MCP server (M1)

`uv run dexatlas-mcp` speaks MCP over stdio and answers eleven questions about a
workspace: the projects, a project's status and how complete its analysis is, the
manifest, the indexed symbols, the source of a class, the source of one exact
method, the calls into and out of a method, an evidence record, and the place a
provenance locator names.

It reads and nothing else — no writes, no shell, no model provider. Three rules
are stated in the tools themselves rather than only in the documentation: every
answer says which backends were missing and whether a limit stopped the analysis
short, because a count is only as good as the analysis behind it; an ambiguous
name is answered with the candidates rather than with one of them; and everything
that comes out of an APK is **data, not instruction**, carried in a field that
says so. A project whose Apktool step never ran gets a `no_manifest` error that
names the backends which did not take part — not `unknown_project`, which means
something else.

```bash
uv sync --extra analysis --extra mcp
uv run dexatlas-mcp
```

A client to try it with is in `examples/mcp_client.py`; the tools and their
boundaries are described in `docs/architecture/mcp-server.md`.

### One evidence-first agent (M2)

The agent turns the tools into an answer. One orchestrator, not a swarm: one
loop, one plan, one budget, one state, one report. It plans a bounded series of
tool calls against a workspace, checks that every conclusion it reached has
something behind it, and reports what it found — separated into what was
established, what is a lead, and what is not established.

The parts that make it more than a loop: per-task budgets for tokens, iterations
and execution time; tool-call logging with retries and a circuit breaker; a task
state that is written down, so an interrupted task can be picked up again; an
explicit confirmation before anything sensitive; and three model endpoints behind
one interface — OpenAI-compatible, local, and a scripted one, so the
orchestration is testable without a model key and without a network.

Two properties are load-bearing. It routes its conclusions through the project's
own `EvidenceBuilder` rather than around it, so a model's output can never become
a verified finding. And **it does not read instructions found inside an APK**:
the APK is untrusted input, and there is a test for it that goes red when the
property is taken away.

The design is in `docs/architecture/agent.md`.

### A benchmark that measures, not demonstrates (M3)

Ninety-two tasks over the five first-party samples, each with an independently
checkable expected answer — including eleven `where-source` tasks that ask where
an answer was found, and eleven `unanswerable` tasks whose correct answer is an
absence. Three configurations run over the same questions: one that reads
decompiled source text, one that reads structured symbols and call references,
and the DexAtlas agent. Each sees only the question, the sample, the backend
configuration and a reference number; the marking scheme is held by the scorer
alone.

Eight metrics — correct-answer rate, evidence-grounding rate,
unsupported-assertion rate, false-positive rate, tool-call success rate,
recovery rate, token consumption and execution duration — are computed from one
auditable trace per run, and every reported figure can be regenerated from the
trace file beside it. A metric whose denominator is zero reads `n/a`, never `0%`.

Two measurements are reported, and they are reported separately because they
answer different questions:

- **The scripted run** (`docs/benchmarks/comparison.md`) — its provider is a
  script, so its numbers come back the same on every run.
- **The real-model run** (`docs/benchmarks/comparison-real.md`) — 92 tasks × 3
  configurations against MiniMax-M3.1-Flash over an OpenAI-compatible endpoint.
  The agent configuration grounded 95.6% of its assertions in evidence and left
  4.4% unsupported, against 0.0% grounded and 100% unsupported for both baseline
  configurations; its overall correct-answer rate was lower (19.6% against
  30.4% and 22.8%), and the report's "Why the failed tasks failed" table says
  why: mostly a model that keeps asking for tools until its budget runs out. On
  the questions whose answer is an absence, the agent was the best of the three.

A CI job (`M3 comparison stays reproducible`) recomputes the eight metrics from
the committed traces on every push, so the reports cannot drift away from their
data. See [Known limitations](#known-limitations) for what a real-model run does
and does not promise.

### The web workbench, six of its eight screens

`dexatlas-workbench` serves a read-only browser over a workspace on
`http://127.0.0.1:8618`:

| # | Screen | Status in this release |
|---|---|---|
| 1 | Project dashboard with backend status | built |
| 2 | APK upload and analysis progress | built |
| 3 | Package / class / method explorer | search + source viewer |
| 4 | Java & Smali source viewer with location links | source + locator resolution |
| 5 | Call graph and cross-reference navigation | built, one method at a time |
| 6 | Agent workspace | built |
| 7 | Evidence viewer | records + provenance |
| 8 | Benchmark and report export | report export built; the benchmark half is not |

The upload screen hands an APK to exactly the same pipeline the REST API and the
CLI run — the same staging, the same 256 MiB limit, the same validation, the same
refusals, one shared implementation in `dexatlas.api.uploads` rather than a copy —
and analyses it in the background while the browser polls the project's status.
An APK that was analysed before is answered with its project, not analysed again.

Every screen sits on the MCP tools' own functions, called in-process: the JSON
the browser receives is the shape the MCP server would have returned, produced by
the same code — no added analysis, no writes, and no second contract. A test
asserts the response against the tool's own `model_dump()`.

Two answers the call-graph screen refuses to fake: a method nobody calls is `0`
call sites, not a 404 — "the analysis read no call into this method" and "this
method does not exist" are different answers — and no number is drawn beside a
callee, because `find_callees` deduplicates its callees and answers no per-callee
count, so such a number would be one no query can re-derive.

The agent-workspace screen runs the production orchestrator over a configured
model endpoint as a background task and shows the plan, the tool-call timeline
and the three-part report. The endpoint is configuration, not convention:
`DEXATLAS_AGENT_BASE_URL`, `DEXATLAS_AGENT_MODEL`, `DEXATLAS_AGENT_API_KEY` and
the optional `DEXATLAS_AGENT_PROVIDER` are read from the serving process's
environment. The key travels in request headers only — never to disk, never into
a task state, an event or a report — and with nothing configured the question is
refused with `503 agent_not_configured` rather than answered by a stand-in model.

```bash
uv sync --extra dev --extra analysis --extra mcp
uv run dexatlas-workbench
```

The screens and the decisions they were built under:
`docs/architecture/workbench.md`.

### The defects the real-model run and the acceptance pass found

The scripted provider always answered in exactly the shape the code asked for,
so four defects were invisible until a real endpoint answered:

- **A real endpoint refused the agent's own tool answers.** The OpenAI shape
  reserves the `tool` role for the answer to a call the *model* made; an answer
  to a call the *plan* made has no such entry, and a strict endpoint rejected it
  with a 400 on the agent's first observation, every time. Such an answer goes in
  the `user` channel now, with the same notice that says it is data.
- **A model that answered in prose lost its answer.** The parser accepted the
  whole reply only if the *entire* reply was the JSON document, so a model that
  wrote its reasoning first had its conclusion recorded as "no answer". The
  document is found inside the answer now, and the prose around it is kept.
- **"What does this method call" was answered with "who calls this method".**
  `find_callees` and `find_callers` ran the same query — both looked the *callee*
  up. Every word of the answer was true, and all of it was about another thing;
  the test beside it counted two numbers and never checked the direction.
- **A note about the analysis could carry a conclusion.** The verifier counted
  "the analysis is incomplete: apktool did not take part" as support for a
  conclusion. A record that says the evidence was insufficient can no longer be
  the ground a conclusion stands on.

The M4 acceptance rehearsal — a new user walking the repository's own
installation, CLI, API and workbench instructions, checked against the plan's
six exit criteria — is recorded in `docs/reports/m4-acceptance.md`. Its
documentation findings are fixed in this release; its verdict on the two screens
that were not yet built is reflected in the table above.

The M4 source review and acceptance (`docs/reports/m4-review.md`) first
recorded a **conditional pass** with two closing conditions. Both were verified
the same day — the agent-question reproduction by the post-fix real-model
re-run (`docs/reports/m4-e2e-run.md` §5, commit `b6e5fb1`), and the bilingual
README agent sections (commit `6eee294`) — and the verdict was upgraded to
**pass** (§5.2 of the review). The disclosure that a question can still exhaust
its budget under the default settings stands: it is model-behaviour tuning,
not an engineering gap.

### The defects the Phase 1 source review found, fixed

The review's 44 findings were re-verified one by one, and the ones this release
fixes are fixed with a test that goes red when the fix is reverted. The ones a
reader of a report could have been misled by:

- **An upload's file name was the client's to choose.** Two different APKs
  uploaded under the same name landed on the same path, and the analysis of the
  first one read the *second* APK's bytes — while the project's hash, identifier
  and every provenance record truthfully named the first. The evidence chain was
  self-consistent and pointed at the wrong thing. Files are stored under their
  own hash now.
- **The default configuration did not decompile Java.** The JADX backend handed
  the same relative path to the child process twice — once as `--output-dir` and
  once as its working directory — so the sources landed in a nested copy of the
  tree the index reads: the report lost the decompilation row and fell back to
  Smali while the tool-version line still credited jadx.
- **A read of the database was a write.** The journal mode was set on every
  connection, so every read took the one write lock SQLite allows and a second
  request failed with `database is locked`. It is set once, where the database is
  created.
- **An analysis that crashed left the project running forever.** An exception
  left the project in `running` with no error recorded, and the API answered
  every later upload of that APK with the existing project — so it was never
  analysed again. A failure now lands the project in `failed` with the error on
  it, and analysis failures have an exit code of their own (3).
- **Reaching a limit truncated the index silently.** The three limits in the
  Androguard adapter stopped the walk and logged a warning; the project then
  reported `completed` with no errors, and the report's counts faithfully
  recorded an index that had been cut short. A limit now records an
  `output_truncated` error that names the limit and says what was missed. The
  limits are also one budget per analysis, not per DEX file — a four-dex APK
  used to get four times the allowance.
- **A backend that outlived its timeout was not stopped.** On Windows the
  timeout killed the `cmd.exe` whose child was the `java.exe` doing the work, and
  the work carried on. The whole process tree is taken down now.
- **A class name could walk out of the decompiler's output tree.** The JADX
  backend honoured a class name that was already a path — absolute, with a drive
  letter, with a UNC prefix — and read the file it named. The checks now live in
  one place (`dexatlas.core.paths`) and both backends use them; a name that fails
  the check is a 404, not a 500 whose traceback carries the server's directories.
- **The API published the server's paths.** `apk_path`, the JSON report's
  `project.apk.path` and error details carried absolute paths; the file's *name*
  is published now and the workspace root is redacted from error details.
- **The default deployment published an unauthenticated API on every interface.**
  `docker-compose.yml` published it on `0.0.0.0` and the installation guide
  taught the same command. Both publish on `127.0.0.1` now, and the guide says
  what exposing it means.
- **A hostile class name could crash the analysis**, and **the `LIKE` prefix
  filter did not escape the underscore** — `--prefix com.example.com_ex` also
  matched `com.example.comXex.Gamma`, because `_` is a wildcard in SQL.
- **The manifest's SDK levels come from the APK's bytes.** Apktool writes its own
  rebuilt values into `apktool.yml`, and what it writes is not what the APK says:
  a sample whose binary manifest carries `minSdkVersion=24` decoded to an
  `sdkInfo` of 25. The version fields were verified to agree; the SDK levels are
  read back from the binary manifest now.
- **The upload ceiling is enforced while it streams.** An upload is streamed and
  counted, and refused at 256 MiB while it streams — never held in memory, never
  written in full. An archive whose declared contents exceed 2 GiB, or that
  expands more than a hundredfold, is refused from its ZIP central directory
  before a byte of it is decompressed.
- **Untrusted DEX is parsed in a worker**, so a malformed DEX is a recorded
  failure rather than a process that takes the service down with it.

### The documentation is a measurement too

- **The version claims in the documentation are checked.**
  `scripts/check-version-claims.py` reads the tags, the package version, the
  changelog and the generated figures out of the repository and reports the
  claims that contradict them. It runs in CI.
- **The readme badges are written from the measurement** the report is written
  from, so a badge that says 1321 tests cannot describe a tree that has 1300.
- **A measurement of the report's figures starts from nothing**: stale
  `.coverage*` data is removed before the script measures, so two measurements
  of the same tree cannot disagree.
- **The citation remapper is idempotent**: it moves a citation only where the
  checker says the symbol it names has left the cited range.
- **The report says which run it describes, and whether a later attempt
  published.** The JSON report's schema version moves to 2 (additive keys).

### Changed contracts, stated here

- **The workbench's `/api/health` names the workspace's directory, not its
  absolute path.** A caller that parsed the field as a path would break; the
  field's purpose does not need a path.
- **The report names the run it describes.** An exported report said
  `Status: completed` — the status of the snapshot — with no way for a
  standalone reader to tell that a later analysis had failed. It says so now.
- **The exported report's duration is real.** The API rebuilt the result from
  storage and did not restore the duration — an old workspace says "unknown"
  rather than "0.0 seconds".
- **`search_symbols` marks its name and excerpt as data.** For a string symbol
  the name *is* the string out of the APK; the other tools already carried such
  text in a field with a notice on it, and this one does now too, bounded the
  same way.

## Known limitations

Stated up front, because a tool that hides its blind spots is worse than one that
does not.

- **The workbench is six of eight screens.** The benchmark view is not built —
  its report-export half is, but the measured runs and the comparison the
  benchmark suite produces are not surfaced on a screen. The cross-reference
  screen answers one method at a time rather than rendering a whole-workspace
  call graph. Screens 3, 4 and 7 cover the search, source-reading and
  evidence-record parts of the plan's screens but do not claim the rest.
- **A real-model benchmark run is not reproducible.** Asked at temperature 0,
  the same question twice still does not get the same answer twice: two runs
  over the same tasks differed by about a percentage point in the
  correct-answer rate and by about one percent in the tokens spent. The
  committed report describes the run whose traces sit beside it; a rerun is not
  expected to reproduce it to the digit, and a difference between configurations
  smaller than that spread is noise no row claims.
- **The agent's correct-answer rate is mostly model behaviour.** The gap to the
  baselines comes from a model that keeps asking for tools until its budget runs
  out, not from the tools failing: the tool-call success rate was 98.9%, and the
  failed-task table attributes the misses. A stronger model may move these
  numbers; the harness is how that would be checked.
- **The samples are small** — the largest committed one is under 3 KB. The
  large-APK benchmark (`docs/benchmarks/large-apk.md`) uses a *generated*
  synthetic APK; there is still no real-world hardened APK in the evidence, and
  the obfuscated sample is hand-written obfuscation, not a realistically
  hardened one.
- **Text hard-coded in a layout is still not indexed.** `res/values*/` text
  declarations are read and queryable; `android:text="..."` inside a layout XML
  is not, and `@string/` references are not resolved to a resource-id graph.
- **A truncated run exits 0.** A run that hit a limit records
  `output_truncated` on the project and in the report, but the CLI's exit code
  is still 0 — a caller that reads only the exit code cannot tell a truncated
  run from a complete one without reading the project record.
- **The API has no authentication, by design.** It is a single-user tool;
  the default deployment binds `127.0.0.1`, and exposing it is the operator's
  decision to make behind a reverse proxy.

The Phase 2 issue list (`docs/reports/phase2-issue-list.md`) and the status page
(`docs/status.md`) carry the full open-items list with the decisions behind them.

## Upgrade

```bash
git pull
uv sync --extra dev --extra analysis --extra mcp --extra demo
uv run pytest -q
```

The analysis core's contracts are the ones M0 rebuilt; the CLI and REST API stay
backward-compatible, with two stated exceptions: an ambiguous method name now
answers exit code 4 / HTTP 409 with the candidates instead of guessing, and the
workbench's `/api/health` names the workspace's directory instead of printing
its path. A workspace indexed by an earlier version still reads: the
cross-reference table is rebuilt on open, and old locators read back in the
current form.
