# Handover

This is the note for whoever picks the project up next — on another machine,
or in three weeks. It says where the project stands, how to get it running,
and what to do next.

Everything here is derivable from the repository. This document only says
**where to look**, so that nobody has to read the whole tree to find out
what state it is in.

The state itself is the tag **`handover-2026-11-10`**, which is the tip of
`main` at the moment this was written.

## 2. Getting it running on a new machine

```bash
git clone https://github.com/gg320324492-lgtm/dexatlas.git
cd dexatlas
uv sync --extra dev --extra analysis --extra mcp
```

The three extras are all needed for the full suite: `dev` for the tools,
`analysis` for Androguard, and **`mcp` for the MCP server** — the lint job
cannot see `src/dexatlas/mcp/server.py` without it, and the MCP tests cannot
import the SDK. That is not a subtlety: CI was red for a whole milestone
because the extra was missing from four jobs.

Then the two external backends. Either way installs the same versions CI
uses:

```bash
# on a fast link
bash scripts/install-backends.sh

# on a slow one: the GitHub release CDN gives one connection ~40 KB/s, and
# the archive is fetched as parallel byte ranges instead (35 minutes -> 2)
uv run --no-sync python scripts/fetch-jadx.py --dest .scratch/backends
```

Point DexAtlas at them, and at a scratch area that is **inside the project
folder** (the system drive is nearly full):

```bash
export DEXATLAS_JADX_PATH="$PWD/.scratch/backends/jadx/bin/jadx.bat"
export DEXATLAS_APKTOOL_JAR="$PWD/.scratch/backends/apktool.jar"
export UV_CACHE_DIR="$PWD/.scratch/uv-cache"
export TMPDIR="$PWD/.scratch/tmp" TEMP="$PWD/.scratch/tmp" TMP="$PWD/.scratch/tmp"
```

Finally the fixtures, and the suite:

```bash
bash scripts/fetch-fixtures.sh
uv run --no-sync pytest -q
```

**A backend that cannot be found makes its tests skip, and a skip is not a
pass.** Read the skip count in the summary line, not just the exit code.

## 3. What to do next

### M3 — the baselines and the metrics

The task set exists: 81 questions over the first-party samples, each with an
expected answer that was checked against the sample's own sources rather than
against the tool's output. `docs/benchmarks/task-set.md` says how each
answer is judged, how a reader can confirm one without running anything, and
how the set could be gamed.

What is missing is the **comparison**. The milestone asks for three
configurations over the same tasks, the same model and comparable budgets:

| | |
|---|---|
| **A** | an LLM with decompiled source-text retrieval |
| **B** | an LLM with structured symbol search and call references |
| **DexAtlas agent** | structured tools, provenance resolution, completeness awareness, evidence verification |

and for the metrics to be regenerable by a script in the repository:
correct-answer rate · evidence-grounding rate · **unsupported-assertion rate**
· false-positive rate · tool-call success rate · recovery rate · token
consumption · execution duration.

The exit criteria to read before starting:
[§5 of the Phase 2 plan](roadmap/phase2-plan.md). Two of them are the hard
ones — *every reported metric can be regenerated by a script in the
repository*, and *a comparison never claims an improvement the measurements do
not support*.

**There is no model key on this machine.** The environment has an
`ANTHROPIC_BASE_URL` and no key, so configurations A and B cannot be run
against a real model here. The agent package has three providers behind one
interface (`providers/openai_compat.py`, `providers/local.py`,
`providers/scripted.py`), and the scripted one is what the tests use. If A and
B are measured with the scripted provider, the report has to say **that is
what they were measured with** — a scripted baseline is not a model baseline,
and the difference between the two is the whole point of the comparison.

The honest sequence: build the comparison harness and the metric script
first, run it against the scripted provider to prove the machinery works,
then run it against a real model as soon as a key exists. Say which is which
in the report, in the same words the rest of this project uses for it.

### M4 — the web workbench

Not started. The plan is in

contract it should sit on: it is already read-only, bounded, and needs no
model, so a workbench can be a reader of the workspace rather than a second

## 4. The gates

The order matters, and it is the order the CI recomputes things in:

```bash
uv run --no-sync ruff check .
uv run --no-sync ruff format --check .
uv run --no-sync mypy
uv run --no-sync python scripts/check-doc-citations.py
uv run --no-sync python scripts/check-version-claims.py --base auto
uv run --no-sync pytest -q
```

**Change the code, format it, and only then measure.** The report records a
fingerprint of `src/` and `tests/`, and CI recomputes it — so a measurement
taken before `ruff format` describes a tree that no longer exists, and the
build goes red on a tree that is perfectly fine. `CLAUDE.md`, `AGENTS.md` and
`docs/` are not in the fingerprint, so changing them needs no re-measurement.

To re-measure and write the figures:

```bash
uv run --no-sync python scripts/refresh-report-figures.py
```

It writes the report's figures and the README badge **only when the
measurement is complete** — every test ran, none was skipped. A partial run
keeps the old figures, which leaves the record describing a tree that no
longer exists. Run it with **all three backends present**, or the skipped
tests make it a partial measurement.

CI runs six jobs: lint/format/mypy, tests on Python 3.12 (every backend),
tests on Python 3.13 (no external backends), tests with Apktool only, the
Docker image, and the dependency audit. Those are three separate backend
configurations, not one, and each is worth running by hand before a push.

### The scripts that were local and now are not

The workflow used to live in a scratch directory that was never committed, so
it died with the machine. It is in the repository now:

| | |
|---|---|
| `scripts/remap-citations.py` | re-derives the documents' `file:line` citations after the code moves. It is **idempotent** — it moves a citation only when the checker says the symbol it names has left the cited range — and it leaves the citations that point at a place rather than at a symbol to the checker and to a person. |
| `scripts/check-doc-citations.py` | the authority on what a citation has to say. It walks the tree once now instead of once per citation, which is the difference between a second and a quarter of an hour. |
| `scripts/accept-chip.sh` | the whole acceptance of one branch: merge, remap, add the report's test-file rows, re-measure, run the gates. It stops before the commit, so a reviewer reads the diff. |
| `scripts/prove-red.sh` | puts the pre-fix version of a file back under the new test, in a throwaway worktree, and shows the test going red. This is what rule 1 of `CLAUDE.md` asks for. |
| `scripts/linux-check.sh` | copies the tree into WSL and runs the suite on real Linux. Run it **from inside WSL** — it copies a Linux path and builds a Linux virtualenv. |

## 5. What this round of work found, and what to watch for

Nine defects came out of putting the MCP server, the agent and the
cross-reference work together. **Every one of them is the same shape: a
sentence that was true about something else.**

- `get_manifest` answered `unknown_project` when the project was there and
  the analysis held no manifest — words meant for a project that does not
  exist, said about one that does.
- `find_callees` ran the same query as `find_callers`, so "what does this
  method call" was answered with "who calls this method". The test beside
  it counted the two numbers and never checked the direction, so it was
  green.
- Whether a class's source could be read was decided by asking whether JADX
  was *installed* rather than by looking at what the analysis produced, so
  the same workspace answered differently on a different machine.
- A cross-reference record's summary said "called from one location" beside
  a detail that said two call sites, and "a location" now means a call site.
- The agent wrote its records under keys the reports do not read, so the
  report counted them as one and one whatever the tool had found.

**What to watch for:** a number that is right and a name that is wrong, a
test that checks the count but not the direction, a machine's state standing
in for an analysis's, and a record that says something about the analysis
being read as if it said something about the APK.

Two more, both about the gates rather than the product:

- **CI was red for a whole milestone.** The `mcp` extra was missing from
  four jobs, so mypy could not see the MCP server. It was green locally the
  entire time. **"Pushed" is not "green"** — look at the result.
- **One test failed only on Linux.** A dead local port is refused
  immediately on Windows and dropped on Linux, so the provider's message was
  different and the assertion was about the machine's networking rather than
  the orchestration's behaviour. The Linux check exists for exactly this.

## 6. The branches

`main` is the branch of record, and it is where the work is.

`claude/p2-003-call-sites-bf978d` is **deliberately not merged**. It stores
one row per *edge* in a table called `xrefs`; `main` stores the *call sites*
in a table called `call_sites`, with the DEX file and the instruction offset
in the key, and derives the edges from them. The difference matters: a site
says *where*, so a citation can be followed to the bytes, and the two units
cannot disagree because one of them is computed from the other. The branch is
kept on `origin` as a record of the other design.

Every other branch on `origin` is merged and can be deleted.

## 7. What is not in the repository, and why

- **The analysis backends** (JADX, Apktool) are third-party binaries. They
  are installed by `scripts/install-backends.sh` or
  `scripts/fetch-jadx.py`, never committed.
- **The fixtures** under `fixtures/apk/` are fetched by
  `scripts/fetch-fixtures.sh` from Apache-2.0 licensed data.
- **`.scratch/`** is this machine's local state: the backends, the uv cache,
  the temporary files, the helper scripts that predate the ones in
  `scripts/`. Nothing in it is needed to rebuild the project, and nothing in
  it is worth keeping.
- **The samples** under `examples/` are first-party, with their sources
  beside them, and they *are* committed — a stranger needs them to run an
  analysis after cloning.
